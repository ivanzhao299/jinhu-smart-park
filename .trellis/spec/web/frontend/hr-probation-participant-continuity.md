# Probation and job-change application continuity

Probation participant state is separate from the paged employee directory. Editing seeds every authorized application participant ID, label and planned date. Candidate page/search/error changes never replace that array. Add/remove/date changes are deliberate, and writer payload derives from the entire controlled array, not visible checkbox fields. The backend replaces all pending participants, so incomplete UI projection must not silently truncate the request. Missing names/unknown states do not authorize inferred identity/date. Planned and confirmed dates remain separate.

Native candidate selector is optional for probation since Add clears it; full participant/date validation owns Save. Preserve contract/lifecycle required selector and original contract one-ID callback. Existing authorized application participants can be maintained without directory authority; no directory bypass or new permission.

Complete authenticated context changes clear editor/rows/candidates. List page replacement does not clear an intentionally retained draft participant set. Errors need retries for the request that failed.

Job-change authorized edit seeds employee/org/position fallbacks from that application when options fail; deliberate organization replacement must not retain an inconsistent old position. Shanghai businessDate controls date defaults and effective-day UI, with backend state/scope/currentemployee validators authoritative. Desktop/mobile cards must be visible using DS with layout-only route grid; use normal business labels, no old/new data split.

Use ordinary `onSubmit` with `event.preventDefault()` for these editable forms and explicitly reset only after a successful write. On rejected writes, names, dates, reasons and complete participant state must retain edited values. Native form validity still applies.
