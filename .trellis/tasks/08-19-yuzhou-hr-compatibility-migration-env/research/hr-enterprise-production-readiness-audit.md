# HR 企业级生产就绪审计（2026-08-20）

## 结论

当前 Jinhu HR 已具备员工主档、入转调离状态机、目标分解、日报/周报/月报、绩效、360、薪酬工资、工资条和审批基础；T0 已用玉舟只读真实备份完成 138 个组织、18 个岗位、2,949 名员工的抽取、转换、装载、核对、隔离和精确回滚。

当前状态仍是“生产级基础 + 迁移实验室”，不是完整企业级 HR。玉舟历史异动、劳动合同、月历模板和五险一金历史兼容已进入规范化目标模型；主要缺口转为历史工资、附件、招聘、培训、奖惩，以及在线考勤异常/请假/加班业务闭环。薪资计算仍是首版简化逻辑，不能直接替代企业正式发薪。

## 生产级硬门槛

1. 数据库：所有旧领域使用前向迁移、批次/映射/错误/校验/回滚证据；金额使用 `numeric` 和十进制字符串，不经 JavaScript `Number` 做权威汇总。
2. 安全：身份证、银行卡、手机号、工资和附件按字段权限投影；旧密码不迁移；迁移报告只保留聚合或不可逆身份哈希。
3. 业务：合同、异动、考勤、社保、工资均采用显式状态机；已确认快照不可原地修改；未知旧状态进入人工裁决队列。
4. 并发与幂等：关键状态转换在数据库事务和行锁内决定；重放与新请求区分；失败停止后续阶段。
5. 运维：每个切片必须经过隔离 PostgreSQL 全链迁移、真实源重复抽取、回滚/重载、日志脱敏、失败清理和资源残留检查。
6. 验收：HR 管理员、部门负责人、员工三类角色完成桌面与 390px UAT；API 权限和组织树数据范围不能依赖前端隐藏。

## 顺序与范围

数据库阶段按 T1 异动 → T2 合同 → T3 考勤/社保 → T4 历史工资 → T5 附件及扩展领域顺序推进。每个阶段先完成 catalog/profile/mapping，再建目标表和 loader，最后执行真实迁移、核对、回滚、重载。生产切换、正式发薪和批量通知不属于数据库实验阶段，必须另设批准门禁。
