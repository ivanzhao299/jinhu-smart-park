# PSW-002 园区授权完整性与目标园区配角

## Goal

让管理员能直接识别用户在每个可访问园区的业务角色完整性，并在不修改用户默认园区的前提下为指定目标园区配置角色；同时让用户在切换前看到自己的目标园区角色摘要，且不扩大角色诊断信息的可见范围。

## Confirmed facts

- `rel_user_park` 只表达园区访问权，`rel_user_role` 才表达目标园区业务授权；access-only 是 D2 明确允许的合法持久状态，不自动补角。
- 当前用户角色读取/写入都从 `sys_user.park_id` 推导目标园区，造成“改默认园区→保存→重开→配角色”的两阶段操作。
- 当前 `accessible_parks` 没有角色摘要；用户列表也只投影默认园区角色。
- 当前园区切换在目标上下文重新求值角色与权限，不复制旧园区权限；PSW-002 不改变该授权语义。
- GitHub Issue：#468。

## Requirements

- 用户管理的移动卡片、桌面列表和编辑面板按每个 accessible park 展示角色摘要与完整性状态。
- accessible park 没有有效业务角色时使用危险色明确显示“可切换但无业务角色”；不得猜测或自动复制角色。
- 新增显式 target-park 角色配置 API；读取候选角色和提交角色绑定都必须显式指定目标园区，不能依赖用户默认园区。
- 普通园区角色管理员只能配置自己当前园区中已获得访问权的用户；受保护租户超级管理员可配置同租户任一有效目标园区。跨租户、不可访问、停用/删除园区、foreign/protected/disabled 角色全部 fail-closed。
- 角色替换保持事务、锁、幂等和审计；审计 scope 使用实际 target park，正文不记录敏感角色诊断细节。
- 园区切换器在选择前显示当前用户自己的目标园区角色名称摘要；无角色时显示“未配置园区角色”。只返回本人已获访问园区的最小摘要，不返回权限码、数据范围、候选角色、其他用户诊断或内部失败原因。
- 角色授权变更按既有约定在刷新、重登或重新获取 context 后生效，不承诺旧 token 即时推送。
- 保持桌面与移动端两个园区切换器行为一致。
- 不改 HR，不直操作生产，不自动修复历史 access-only 数据。

## Acceptance Criteria

- [ ] 管理员可在用户的每个 accessible park 看到有效角色名称/数量与完整性；access-only 精确标红“可切换但无业务角色”。
- [ ] 管理员可选择 target park，加载该园区候选/已绑定角色并一次提交；用户默认园区不发生变化。
- [ ] 非 super 管理员不能跨当前园区配角；super 也不能跨租户；目标用户必须拥有目标园区 access。
- [ ] 角色写入只替换目标园区的可管理绑定，不触碰其他园区或受保护绑定；重复 role ID、越界角色和无效目标均拒绝。
- [ ] 普通用户只可看到自己的已授权园区及最小角色摘要；任一拒绝/异常响应不泄露角色、权限、SQL 或目标存在性诊断。
- [ ] 桌面与移动园区切换器均在切换前显示目标角色摘要，无角色显示“未配置园区角色”。
- [ ] API/Web 定向测试、shared build、typecheck、lint/build 与相关回归通过。
- [ ] PR `Closes #468`，Codex review 不超过 3 轮，PR CI、合入后 main CI 与 Deploy Production 双绿。

## Out of Scope

- PSW-003 的 access-only 专用可恢复空态。
- D5 历史 access-only 审计清单与任何自动修复。
- 默认角色继承、跨园区复制角色或改变 protected tenant super 语义。
- 逐业务 endpoint 的完整授权审计。

## Open Questions

- 无。D2、权限边界与队列顺序已由用户批准，并由现有授权模型约束。
