# 组织上下级与组织层级能力设计

## 1. 设计目标

在保留 `sys_org.parent_id` 邻接表模型和现有 API 兼容性的前提下，补齐组织树读取、层级写入校验、用户组织岗位关系和 `org_and_children` 递归授权，形成从数据库、API、权限到 Web 的完整闭环。

## 2. 架构边界

### 2.1 组织层级

- 保留现有 `GET /orgs` 分页平铺接口。
- 新增 `GET /orgs/tree`，返回当前租户和园区内的树形结果；兄弟节点按 `sortOrder`、`orgName`、`id` 稳定排序。
- 树节点沿用组织基础字段并增加 `children`，共享契约中定义明确类型，Web 不直接拼装未类型化 payload。
- 新增/修改父级时由服务层统一校验：父组织存在且有效、作用域一致、不能为自身、不能为当前节点后代。
- 删除存在有效子组织或有效用户组织关系的组织时拒绝操作。停用时拒绝新增关系，但保留历史可见性。

### 2.2 数据库

- 新建前向迁移，不修改 `000002` 或 `000175`。
- 在迁移前检测现有孤儿父级、自引用和循环；发现异常时失败并给出可定位信息，不静默修复业务数据。
- 为 `(tenant_id, park_id, parent_id)` 增加层级查询索引。
- 在兼容存量数据验证通过后，为 `parent_id` 增加指向 `sys_org(id)` 的自引用外键；业务层继续负责同租户/园区和防环校验。
- 为有效 `rel_user_org` 增加用户—组织—岗位关系唯一性，并通过部分唯一索引保证每个用户在同一作用域最多一个有效主组织。

## 3. 用户组织与岗位

- 在现有 `UsersService` 边界内提供用户组织关系列表与替换式更新，避免部分写入造成多个主组织。
- 写入采用事务：校验用户、组织、岗位作用域和状态后，一次性同步关系。
- 岗位必须存在且有效；若岗位与组织没有独立绑定模型，则第一版只校验同租户/园区，不虚构组织—岗位绑定关系。
- 用户详情响应增加可选的组织关系集合，保留既有用户字段与现有创建/更新调用兼容。
- Web 用户页增加主组织、兼任组织和岗位维护入口，并明确展示失效历史关系。

## 4. 数据权限

- `org_and_children` 以规则中的显式根组织 ID 为输入，递归展开当前租户/园区内全部有效后代，再交给现有 `IN(ids)` 过滤链。
- 对重复根、重叠子树做去重；空根维持无权限结果，不能回退成全量。
- `self`、`all`、显式 `org` 等现有 scope 类型语义保持不变。
- 递归查询必须限定租户、园区和 `is_deleted=false`；停用组织是否参与历史查询沿用具体资源现有状态规则，授权集合默认只纳入有效组织。

## 5. Web 交互

- 组织页面桌面端展示可展开树，移动端展示层级卡片；保留搜索和状态筛选。
- 新增/编辑抽屉增加父组织和负责人选择；编辑时前端排除自身及后代，后端仍作最终校验。
- 删除存在子组织/用户关系时展示服务端中文业务错误。
- 用户页使用共享选择组件维护组织与岗位，确保 390px 宽度无横向溢出。

## 6. 兼容性与回滚

- 现有分页列表、详情和 CRUD URL 不变；新增字段均保持可选或向后兼容。
- 数据迁移只增加约束和索引，不重写既有层级。
- 若递归授权出现问题，可独立回滚应用层展开逻辑；数据库迁移保持前向修复，不编辑已执行迁移。
- 角色树、权限树不属于本任务，避免把其 `parentId/level` 语义混入组织模型。

## 7. 分阶段验收

1. 组织树契约、数据库完整性和后端层级校验。
2. 用户组织/岗位/主组织事务化维护。
3. `org_and_children` 递归权限生效及回归。
4. Web 组织树、用户组织维护、桌面与移动端验收。
5. 首发回归脚本、文档同步和完整质量门禁。
