# Android 原生多门户客户端重构

## Goal

将现有以 WebView 为主体的 Android 薄壳重构为面向现场高频使用的原生 Android 客户端。在一个可安装、可升级的 APP 中提供员工端与业主/租户端两个业务门户，并严格依据服务端角色、权限、园区范围、字段策略和已开通模块开放功能。

## Confirmed Facts

- 当前 `android-app` 是 Kotlin WebView 薄壳，已具备正式签名、APK 构建、版本清单、登录后下载入口、应用内升级和独立轻量部署链。
- `/users/me` 已返回角色、权限、数据范围、字段策略、已开通模块、菜单树、当前园区及可访问园区，可作为原生客户端授权事实源。
- Web 已有员工现场入口 `/operations/terminal`、工程入口 `/engineering/terminal` 和业主/租户入口 `/tenant/service`，对应业务 API 可优先复用。
- API 端已经通过权限守卫和模块守卫实施服务端授权；客户端权限控制只能改善体验，不能替代服务端鉴权。

## Requirements

- 采用一个 Android APP、两个业务门户：员工端和业主/租户端；同时具备两类权限的用户可在应用内切换门户。
- 登录后由服务端上下文决定可进入的门户、首页卡片、快捷动作、数据范围和可执行操作，客户端不得维护独立的静态角色真相表。
- 员工端首期覆盖：今日任务、工程/安全巡检、工单处理、隐患上报、拍照、定位、离线草稿、待上传队列和消息提醒。
- 业主/租户端首期覆盖：服务报修/诉求提交、进度查询、补充照片、处理结果确认/评价、园区通知和常用联系人/房屋位置选择。
- 表单遵循现场极简原则：主流程控制在两到三个核心动作，除照片和必要说明外优先使用服务端候选项、下拉选择和自动带入。
- 原生端必须支持多园区上下文切换；所有业务请求携带当前租户/园区上下文，并在切换时清理或隔离缓存与草稿。
- 原生端必须复用现有 API 权限和模块开通规则；新增移动聚合接口时也必须声明权限、模块、数据范围和字段策略。
- 原生端支持安全令牌存储、令牌刷新/失效处理、HTTPS、日志脱敏、截图/文件权限最小化和远程退出。
- 首期 Android 技术栈采用 Kotlin、Jetpack Compose、MVVM/单向数据流、Retrofit/OkHttp、Room/DataStore、WorkManager、CameraX 和系统定位服务。
- 旧 WebView 业务在迁移期保留为受控兜底，仅针对尚未原生化且被明确列入白名单的低频功能开放；核心现场流程不得继续依赖 WebView。
- 继续复用当前签名、APK 下载、版本清单与 Android CI；客户端发布与服务端/API/数据库发布按变更分级独立执行。
- 本任务当前仅完成方案与实施计划，不启动代码实现或生产部署。

## MVP Feature Priority

### P0：试点上线必须具备

- 通用：密码登录、会话恢复、退出、多园区切换、双门户路由、权限刷新、应用升级、消息中心基础列表。
- 员工端：今日巡检、巡检执行、异常拍照、定位、结果提交、我的工单、接单/到场/完成、快速隐患上报、离线草稿和上传队列。
- 业主/租户端：创建报修/服务请求、选择服务类型与标准位置、照片上传、我的请求、状态时间线、完成确认与评价。
- 管理：移动 capability 配置、最低客户端版本、模块开关、试点用户开关和客户端运行指标。

### P1：试点稳定后补齐

- 推送通知、扫码识别设备/巡检点、语音转文字、消息已读状态。
- 工单补充材料、转派可见性、隐患整改/复查、巡检路线导航。
- 业主园区公告、常用联系人、常用位置和服务评价统计。

### P2：不阻塞首发

- 生物识别快捷解锁、应用商店上架、地图轨迹、实时聊天、iOS 客户端。

## Role And Portal Rules

- 员工门户不是由角色名称硬编码判断，而是用户至少拥有一个员工端 capability 后开放。
- 业主/租户门户不是由用户名或组织名称推断，而是由服务端身份关系、模块和 capability 联合判定。
- 同一账号同时拥有两个门户时允许切换，但同一业务记录的数据范围始终由 API 重新校验。
- 超级管理员不自动进入员工门户或业主门户；仍需目标园区模块可用，避免把管理后台权限等同于现场身份。
- 权限或模块在服务端被撤回后，客户端下一次启动、恢复前台或收到 403 时立即刷新 bootstrap，并清除不可再访问的内存数据。

## Acceptance Criteria

- [ ] 登录后能够根据服务端上下文准确显示员工端、业主/租户端或双门户选择，未授权门户不可见且 API 访问仍被服务端拒绝。
- [ ] 员工端用户可在原生界面完成“查看今日任务 → 到场/开始 → 拍照与结果选择 → 提交”闭环。
- [ ] 业主/租户用户可在原生界面完成“选择服务类型与位置 → 拍照提交 → 查看进度 → 确认/评价”闭环。
- [ ] 多角色、多园区、模块关闭、权限撤回、账号禁用和令牌失效均有自动化权限矩阵测试。
- [ ] 断网时可保存草稿和照片队列，恢复网络后可见、可重试且不会重复提交。
- [ ] 核心页面无 WebView，支持 Android 返回导航、系统权限拒绝后的恢复路径和进程重启后的状态恢复。
- [ ] 原生端冷启动、列表加载、图片压缩上传和崩溃率达到试点验收基线，并有可观测指标。
- [ ] 新旧客户端可并行运行；发生严重问题时可通过版本清单/功能开关停止升级或关闭新模块，不影响现有 Web 业务。
- [ ] Android CI 能分别产出内部测试、试点和生产版本，签名一致，生产下载入口继续有效。
- [ ] 邵明洪等工程人员与至少一名业主/租户代表完成真机 UAT，关键任务闭环通过。
- [ ] P0 页面均有加载、空数据、权限不足、断网、服务端错误和提交成功状态，不出现白屏或无限 loading。
- [ ] 现场主流程从首页到提交不超过 5 个页面层级，单任务常规完成最多 3 个核心动作，除异常说明外不强制长文本输入。
- [ ] 生产试点连续 14 天 crash-free users ≥ 99.5%、ANR < 0.5%、照片上传成功率 ≥ 98%、重复业务提交为 0。
- [ ] 90% 常规巡检任务在 90 秒内完成；90% 业主服务请求在 60 秒内完成提交。
- [ ] P0 权限矩阵和数据隔离测试覆盖员工、业主/租户、双身份、无移动权限、跨园区和权限撤回六类账号。

## Out of Scope for MVP

- iOS 原生客户端。
- 将管理后台全部功能搬到手机端。
- 首期接入应用商店、微信登录、短信登录或即时通讯。
- 在客户端重新设计一套独立 RBAC、菜单或组织架构。

## Open Product Decision

- “业主端”当前按现有产品语义定义为企业租户与业主联系人使用的服务门户；如果用户意指园区资产所有方/领导驾驶舱，需要拆成第三类管理门户并重新调整范围。
