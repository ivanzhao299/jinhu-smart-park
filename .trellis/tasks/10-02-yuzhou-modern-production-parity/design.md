# 技术设计与实施边界

## 1. 延续现有内核

复用 apps/api/src/modules/hr、apps/web/app/hr、packages/shared、现有 hr_ 数据域、Workflow Inbox、RBAC、审计和文件服务。先检查真实实现和测试，逐个补齐缺口，不重新开发已有领域。集成版先达成日常运营，独立版仍是最终产品验收轴，两者共用业务内核。

## 2. 三条证据链独立

- 数据：来源 → 原始归档 → 映射 → 业务投影 → 数量/金额/文件核对。本次三批已成功，禁止重放已消费授权。
- 功能：旧 Windows 客户端与集团 Web 分别建立页面、动作、规则、报表、角色稳定标识 → 现代实现 → 测试 → 运行验收。同名页面和共享目标 route 不证明等价。
- 生产运营：真实业务任务 → API 及页面 → 审批/事务/审计 → 人工岗位验收 → 明确范围启用。导入和技术 UAT 不替代业务签署。

## 3. 历史异常生命周期

使用四种结果：ARCHIVED_HISTORICAL（保留原始证据，退出活跃修复队列）、CURRENT_IMPACT_REVIEW（当前运营风险待人工裁决）、DETERMINISTIC_FIX（有唯一证据可机械修复）、FIXED_VERIFIED（补导/纠正及对账已通过）。未知影响暂为 IMPACT_CHECK_PENDING，不伪装成已归档。

“归档关闭”不等于删除，不将错误事实写入在线业务，不自动恢复为可登录身份，不计为成功业务落库。优先复用现有归档与审计；只有确有查询/处置需求才增加小型接口或前向迁移，禁止为了处理历史垃圾新建庞大工作流。

按员工映射、当前在职/任职、当前有效合同、当前开放薪资/社保期间、实际账号权限进行一次性只读影响关联。保存内部不可逆引用、分类依据、证据 hash、数量和决定；公开材料仅聚合。无法证明历史无影响的记录进入小型核对清单，独立阻断对应业务，不阻断其他模块。

数据修复使用新的受控批次、精确范围、原始值与纠正值并存、重复防护及回滚证据；不修改成功迁移、原载荷或既有导入回执。145 条工资人员映射、6 条照片关联与核心隔离按依赖交叉核对，不能直接相加为人数。

## 4. 当前业务与历史展示分离

保留历史工资不可变快照；展示较早年度的统一查询入口，验证分页、筛选及详情，不以近三年查询界面替代全历史可达性。归档异常显示可理解的缺件/关联状态，不能伪造下载链接。历史原始 SQL 和190条逻辑证据保持惰性，禁止执行旧动态 SQL。

新工资计算只使用已验证、版本化、受限规则；考勤/社保/岗位等输入必须有来源与期间。双轨比较解释差异后再进入正式确认流程。发薪、报盘、税务及银行集成属于明确启用范围，不能被普通测试或历史导入触发。

## 5. 双源与增量

将集团 Web 来源和备份后的新增修改单独纳入范围清单。优先处理当前运营事实；同工号/身份冲突由明确来源优先级和人工裁决解决，禁止按姓名归并或重复创建人员。旧盘点的115个集团 Web 独有在职候选只是历史快照，必须刷新后才行动。历史冷数据可归档保留但仍登记差距，不从全功能等价分母隐去。

## 6. 发布与回退

每个切片从最新 origin/main 建立干净 codex/* 候选，保护当前计划文件及原工作树。先读相关规格和受影响代码，使用聚焦验证；修改输入/代码后失效相关旧测试结果。发布前再次 fetch、验证候选/合并/运行 SHA、health/ready、用户行为，执行 Docker 停止容器、未使用镜像清理，磁盘压力时清理 build cache。

前向迁移只新增，禁止更改成功历史迁移。应用回退与数据回退分开；失败保留证据，不自动覆盖生产库。现有一次性导入授权不能用于新批次或灾备恢复。既有普通开发授权继续有效，不重复询问例行步骤。

## 7. 成本和续接

默认一个代理、一个活跃切片、一个生产迁移写者；不用模型轮询状态。历史影响筛查设置两小时初始工作预算：达到预算则输出已判定分类与当前影响疑点，继续运营建设，不启动大规模逐条旧资料考证。预算不允许把未核验项标为无风险。

每片保存目标、验收、基线SHA、文件责任、验证结果、运行句柄、局部阻断、下一步；私人材料0600/0700。连续两次同因失败做一次聚焦根因检查，不从全量导入重头开始。历史性能优化 PR772 为独立草稿，仅当实测当前运营受影响才取用。

## 8. 工资双轨输入与历史发布的解耦约束

现有路径只接受 published 历史批次，保持不变直至新增来源机制完成验证。staged 并非完全冻结：000248 的 snapshot insert guard 和 000264 的 item statement guard 仍允许追加；批次的已完成导入回执不能单独证明后续输入不会变化。不能只将查询条件扩大为 staged 或删除现有拒绝条件。

独立模拟来源必须先核对实际成功导入控制回执、同一租户园区、批次、期间、已映射员工、记录数和内容 hash。只冻结拟核对期间，不复制全部 1078020 工资明细。明确保留来源表/版本、金额精度、实发项目、公式和考勤/社保/薪酬版本。冻结与核验须在同一事务和一致读视图中；并发追加、回退或来源漂移必须被拒绝或使本次创建失败，不能留下半份冻结输入。

该来源不能改变历史 batch.status、员工历史可见性、正式工资批次、工资条或发薪接口。模拟结果仍为只算不发，真实规则与金额差异由薪酬/财务核对。新机制需要前向迁移、来源隔离与冻结并发的真实 PostgreSQL 测试，并分别验证 HR、负责人和员工权限。

实施顺序：当前运营组合候选先完成 CI 和可发布审查；冻结机制先在隔离数据上验证；业务期间和规则确认后再创建精确范围的生产模拟来源。历史发布与发薪各自保留独立业务决定。
