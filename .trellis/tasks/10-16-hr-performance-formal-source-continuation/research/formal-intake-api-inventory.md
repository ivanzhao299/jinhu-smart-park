### Existing route and signature map
- `POST /hr/performance-v2/templates/channel` → `createChannelTemplate(scope, actor, CreateHrPerformanceChannelTemplateDto)` → `HrPerformanceReviewService.createChannelTemplate`; permission `HR_PERFORMANCE_TEMPLATE_MANAGE`, `IdempotencyInterceptor`, audit `hr.performance_template`, `captureBody:false`.
- `POST /hr/performance-v2/templates/:id/channel-versions` → `createChannelVersion(scope, actor, id, CreateHrPerformanceChannelVersionDto)` → `createChannelVersion`; same template-manage permission and idempotency/audit.
- `POST /hr/performance-v2/template-versions/:id/channel-definition/revisions` → `appendChannelDefinition(scope, actor, id, AppendHrPerformanceChannelDefinitionDto)` → service append, current draft/head CAS, append-only revision.
- `POST /hr/performance-v2/template-versions/:id/channel-workflow/revisions` → `saveChannelWorkflow(...)` → `saveWorkflow(...)`; workflow DTO supplies expected definition and workflow pointers; template-manage permission, transaction locks template parent then version, validates pair, appends workflow revision.
- `POST /hr/performance-v2/templates/:id/publish` → `publishTemplate(scope,actor,id)`; only current draft can publish; five-channel policy must be complete and valid; calculation execution function privilege checked.
- `POST /hr/performance-v2/cycles` → `createCycle(scope,actor,CreateHrPerformanceReviewCycleDto)`; `HR_PERFORMANCE_MANAGE`; requires published template, active org IDs in same tenant/park, stores immutable `template_snapshot` with `status='planning'`.
- `POST /hr/performance-v2/cycles/:id/publish` → `publishCycle(scope,actor,id)`; locks cycle `FOR UPDATE`, selects eligible employees (or explicit `selected_employee_ids`), inserts `hr_performance_cycle_employee` in `self_review`, then calls `channels.initialize(...)` and freezes evidence in the same transaction.
- `PATCH /hr/performance-v2/reviews/:id/channel-input` → `patchChannelInput(scope,actor,id,PatchHrPerformanceChannelInputDto)` → `HrPerformanceChannelWorkflowService.patch`; `IdempotencyInterceptor`, any active stage authority permission among self/manager/calibrate/appeal-review, captureBody false.
- `GET .../reviews/:id/channel-input` and `/history` route through `current` / `history`; each requires visibility rules and metadata-only sensitive-read audit; salary field projection is live-authorized.

### DTO and transaction patterns
- `CreateHrPerformanceTemplateDto` is dimension-only: `templateCode`, `templateName`, `versionName`, 1..30 dimensions and 1..20 levels. Five-channel route instead accepts `CreateHrPerformanceChannelTemplateDto {workflowPolicy?: HrPerformanceWorkflowPolicy, templateCode:string(1..64 nonblank), templateName:string(1..120 nonblank), versionName:string(1..120 nonblank), config:HrPerformanceChannelDefinition}`; `config` is validated by shared `validateHrPerformanceChannelDefinition`.
- `CreateHrPerformanceChannelVersionDto` extends the exact create-template DTO with `expectedVersionId:uuid` (same parent identity/version optimistic concurrency contract). `AppendHrPerformanceChannelDefinitionDto` is `{expectedWorkflowRevisionId?:uuid,workflowPolicy?:HrPerformanceWorkflowPolicy,expectedRevisionId:uuid,config:HrPerformanceChannelDefinition}`; if a workflow pointer already exists, both workflow fields are required by service-level atomic pair validation.
- `SaveHrPerformanceWorkflowPolicyDto` is `{expectedDefinitionRevisionId:uuid,expectedWorkflowRevisionId:uuid|null,policy:HrPerformanceWorkflowPolicy}`. `CreateHrPerformanceReviewCycleDto` is `{cycleCode:string<=64,cycleName:string<=120,startDate:date,endDate:date,templateVersionId:uuid,applicableOrgIds:uuid[1..200]}`; it has no selected-employee field. `PatchHrPerformanceChannelInputDto` is `{expectedRevisionId:uuid,changes:HrPerformanceInputChange[]}` validated by shared `validateHrPerformanceInputChanges`.
- `HrPerformanceChannelWorkflowService.appendWorkflow(m,scope,actor,versionId,definitionId,previousWorkflowId,policy)` inserts immutable revision then updates version head within caller transaction.
- `HrPerformanceChannelWorkflowService.initialize(m,scope,actor,cycleEmployeeId,workflow)` inserts revision 1 using `emptyHrPerformanceChannelInput(workflow)` then advances `hr_performance_cycle_employee.current_input_revision_id`; it is designed to run inside cycle publication transaction. Frozen contract defines the input shape `{schemaVersion:1,details:[{id,itemId,channels:{s,m,t,x,c}}],adjustments:{master,timekeep,bonus},master:{selfAppraisal,appraisal,description,salaryReference}}`; cells are `{state,value,actorUserId,changedAt,evidence}`, with exact all-null adjuncts for UNPROVIDED.
- Cycle source-specific selected cohort can already use `selected_employee_ids` at publish time (cycle corrections use this); normal `CreateHrPerformanceReviewCycleDto` does not expose it. Do not infer that correction-cycle DTO is appropriate for first intake: it requires confirmed predecessors/reason and has correction semantics.

### Critical 371/372 guards
- Migration 371's initial `hr_performance_version_guard` prohibited five-channel publication, and its cycle guard rejected channel cycles. Migration 372 replaces both: current version guard permits only the normal `draft`→`published` transition (with `published_at`), while still freezing version identity and requiring append-only definition-head successors. Current cycle guard permits only an unpublished `planning` insert, and requires the referenced version already `published`, a complete valid workflow, and exact frozen definition/workflow revision IDs/config/policy. Thus publish template before creating cycle; do not repeat 371's superseded blanket prohibition.
- 371 `hr_performance_channel_revision_guard` remains current (372 does not replace it): definition revisions can only append against the current channel draft/head; first revision is revision 1 and already the version head; each successor has exact revision+1/previous pointer. The version may later transition to published under 372's replacement version guard; its definition table remains append-only and deferred `trg_hr_perf_channel_head` enforces advancement.
- 372 `hr_performance_channel_input_revision_guard`: input revisions are append-only; existing rows allow statuses `self_review`, `manager_review`, `calibration`, `appealed`; current pointer must equal `previous_revision_id`; input must validate against frozen cycle workflow.
- 372 baseline case (`previous_revision_id IS NULL`) requires current `hr:performance:manage`, `revision_no=1`, and every cell exactly `UNPROVIDED`. It explicitly rejects a prefilled initial input. Normal `patch` forbids reset to `UNPROVIDED`, requires expected current revision, intersects DTO changes with `allowed()` based on current stage, live permission, employee/manager/calibration membership and field policy, assigns actor/time server-side, then appends a CAS revision.
- 372 changed cells require real selected-park stage role and current permission. Salary writes additionally require live `hr:performance:read`, `hr:performance:manage`, `hr:compensation:manage`; read omits salary unless performance-read AND payroll-detail-read. Self projection hides non-self-stage values and preview absent result-read.

### Minimal additive integration proposal
- Keep existing formal template/version/publish/cycle routes as the normal business creation surfaces. Add one source-intake route/service operation bound to a source receipt/manifest and an explicit source-to-formal target, rather than teaching generic `createTemplate`, `publishCycle`, or PATCH to trust source payloads.
- Minimum new durable integration is a scoped append-only intake receipt/link plus one guarded baseline initialization record or mode marker. In one DB transaction: acquire target cycle employee/review lock; verify receipt qualification and exact manifest; reject if source link already targets this formal review or current input head/revision state is no longer the pristine revision-1 baseline; verify empty/no prior business input and status is still initial `self_review`; validate every source field against the frozen definition/workflow and exact stable detail IDs; generate revision 2 (or the chosen explicitly modeled baseline revision) with source-derived VALUE/EXPLICIT_NULL cells carrying real actor/time and provenance evidence; insert append-only revision plus link/receipt and advance current head atomically. Keep revision 1 all-UNPROVIDED as guard-compliant historical baseline; do not rewrite it.
- New source initializer must be a narrow sibling to `initialize`, not a bypass through `patch`: database guard currently rejects non-UNPROVIDED revision 1 and normal subsequent INSERT enforces actor stage permission. An additive migration can introduce a receipt-bound one-time baseline case for a newly created, still-pristine review, with immutable receipt FK/target binding, manifest CAS, and all normal scope/definition validation retained. It must not permit ordinary callers or future PATCH operations to use that exception.
- For maintainability, create source-derived draft before publication with ordinary channel template APIs, then publish the chosen version, create cycle and explicit selected employee cohort, and publish cycle through ordinary APIs; attach baseline after `channels.initialize` has created revision 1 but before business users start edits. If policy requires baseline values visible before cycle publication, a carefully scoped new intake transaction must create cycle employees and baseline revisions together, preserving `publishCycle`'s cohort/eligibility/evidence behavior. Current route cannot do that without additive service path.
- Store source author/date/legacy review identity as provenance/evidence fields; never convert them to `created_by`, changed-cell actor, self-review submission, manager approval, or final status. Missing source data remains UNPROVIDED or an explicit flagged gap; do not infer 0, NULL, reviewer, role, or approval.
- Full six-family zero-count production observation in parent PRD means no source-eligible existing formal target can be assumed; initial intake must support creating the first normal template/cycle/review pathway while retaining complete parent PRD manifest, provenance, idempotency, duplicate target, conflict/CAS and permission acceptance.
