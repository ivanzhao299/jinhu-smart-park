# 玉舟旧人力资源系统兼容迁移与测试环境

## Goal

以受控玉舟源备份、数据库业务规则及旧页面为依据，完成企业级、独立可复用、全功能现代 HR 产品和受控历史生产迁移。在 Smart Park 中，HR 是完整的专业人力资源子系统；离开 Smart Park 后，仍能携带完整数据、业务规则和历史记录独立部署运行，并可复用于另一家企业。两种模式共用一个产品内核，不能以迁移成功或若干页面完成代替全产品验收。

2026-09-05 用户确认的最终目标与 P0-P4 必验项见 `docs/yuzhou-hr-compatibility-development-plan.md` 第 1 节；机器路线图为 `scripts/hr-cutover/contracts/hr-enterprise-rewrite-roadmap-v2.json`。原 M0-M5 兼容与迁移范围完整保留。以下环境、T0 要求及事实记录属于初始阶段历史，不是最终产品范围或当前运行状态，尤其不能把早期“未找到备份”误作当前阻断。

## Final Product Acceptance

- [ ] P0：业务领域与平台依赖边界完整验证，独立企业不依赖园区业务或伪造园区。
- [ ] P1：同一 HR 内核的集成版和独立版均可部署，基础身份、组织、权限、消息、文件及审计可用。
- [ ] P2：独立版具备专用 HR 数据库及文件边界，独立备份、恢复和身份重绑定可验证。
- [ ] P3：数据、字典、规则版本、历史审批审计、旧映射、批次账本及文件完整迁至另一企业，守恒、重放、恢复与回滚通过。
- [ ] P4：两种模式的角色、业务、历史查询、报表、桌面/390px、性能预算及独立升级验收通过。
- [ ] 原 M0-M5 所有兼容与受控生产迁移验收通过；上述各项须分别有运行证据，不能按平均分核销。

## User Value

- 后续开发者可以一条命令启动 PostgreSQL、API、Web 和旧库只读实验环境，不再依赖个人机器的偶然状态。
- HR 可以确认旧系统 20 多年积累的员工、异动、合同、工资、社保、考勤等数据不会丢失业务语义。
- 数据迁移有批次、映射、错误、校验和回滚证据，能够反复演练，而不是一次性脚本导入。
- 新模块保留旧工号、组织编码、业务单号和历史查询习惯，同时淘汰宽表、动态工资列、明文密码和客户端直连数据库。

## Confirmed Facts

- 材料目录共有 220 个文件，218 个 UTF-8/可解码文本文件共 17,570 行，另有 `.DS_Store` 和 7z 归档；全部文本已逐文件读取，无解码失败。
- `schema_tables.sql` 含 162 张表；对象源码目录实际含 194 个存储过程文件、15 个标量函数、1 个表值函数、2 个触发器。现有报告写“169 个存储过程”，与文件级清单不一致，必须以恢复后的 SQL Server 系统目录再次核定。
- 两份《玉舟 HR 系统功能与数据库结构分析报告》SHA-256 相同，是重复副本。
- 旧系统核心规模：员工 2,949、照片 2,155、组织 138、异动 6,887、合同 802+357、工资约 4.5 万行、五险一金 35,008、附件 1,003。
- Jinhu 已有员工、目标/汇报、绩效/360、薪酬工资和审批基础，但缺合同、考勤、社保、招聘、培训、奖惩、旧编码兼容和通用迁移控制模型。
- 本机是 Apple Silicon arm64、16GB 内存、约 743GB 可用磁盘，Rosetta 已安装；Node 24、pnpm 9、PostgreSQL 16、Python、jq、rg 已就绪。
- 已补齐 Colima、Docker CLI/Compose 和 p7zip；SQL Server 查询使用镜像内 `sqlcmd`。amd64/Rosetta、标准 `pnpm db:*` 链路和 SQL Server 2022 Developer 查询均已实测通过。
- 用户目录没有找到 `.dbk/.bak/.mdf/.bacpac` 原始旧库备份；当前只有分析产物。真实行级迁移必须补充只读源备份或经审批的只读 SQL Server 连接。
- 当前 `main` 相对 `origin/main` ahead 23 / behind 31，且有其他任务 WIP；不得 reset、覆盖、删除或强推。

## Requirements

### 1. 可重复运行环境

- 采用 Colima + Docker CLI/Compose 作为本机容器运行时，支持 Apple Silicon，并为 SQL Server amd64 镜像启用 Rosetta/虚拟化兼容。
- 保留 Homebrew PostgreSQL 16 作为快速本地开发能力，同时提供与仓库一致的 Docker PostgreSQL 16 作为迁移和 Release Smoke 权威环境；二者使用不同端口和显式数据库名，禁止误连。
- 安装 7-Zip 用于材料归档核验；SQL Server 查询优先在容器内执行 `sqlcmd`，必要时再安装本机 ODBC 工具。
- 增加环境诊断和启动/停止/清理脚本，检查端口、磁盘、Docker、PostgreSQL、SQL Server、依赖版本和敏感配置，不提交密码。

### 2. 旧系统事实基线

- 对全部材料生成路径、大小、SHA-256、对象类型和重复件清单。
- 从 DDL、字段字典、字典数据、帮助文档和全部数据库对象源码建立功能→表→过程→新领域映射。
- 对“169 个存储过程”与“194 个过程文件”的差异给出 catalog 级解释；无法从资料证明的事实标记 `UNKNOWN`。

### 3. 兼容与迁移策略

- 业务语义兼容，不复制旧物理结构：保留旧工号、组织编码、JZ/DZ/LZ/FZ 单号、合同号、账套、工资项目、原始状态和历史日期。
- 建立 `legacy_source_object`、`legacy_record_map`、`migration_batch`、`migration_batch_item`、`migration_error`、`migration_check`、`migration_rollback_point` 等控制模型。
- 全量迁移员工、组织、异动、合同、社保、历史工资、附件及高价值业务历史；历史工资按不可变原始快照迁入查询层，不用现行规则重算旧结果。
- 旧工资公式转换为白名单 DSL；无法安全解析的公式进入人工复核，不允许执行任意 SQL/表达式。
- 旧明文密码永不迁入登录凭据；仅保留不可逆迁移证明或身份映射，所有用户强制新凭据流程。
- 照片和附件按魔数、大小、哈希验证后进入共享文件体系，保留旧对象和记录映射。

### 4. 安全与生产边界

- 原始旧库只读挂载，ETL 使用独立只读账号；迁移写入仅针对显式命名的一次性 PostgreSQL 数据库。
- 数据迁移脚本必须要求 loopback 地址、隔离数据库名、run id 和显式 mutation flag，默认拒绝生产/共享库。
- 日志、报告和错误样本不得输出身份证、银行卡、明文密码、完整手机号、工资明细或数据库 URL。
- 迁移、生产种子、管理员初始化和 UAT 严格分离；失败后停止后续步骤。

## Acceptance Criteria

- [ ] 环境诊断脚本能明确报告并验证 Node/pnpm、Docker Compose、PostgreSQL 16、SQL Server 只读源、7-Zip 和仓库依赖状态。
- [ ] `pnpm db:up`、迁移、生产安全种子、初始化检查和 API 登录 smoke 可在隔离环境按标准顺序执行。
- [ ] SQL Server 兼容实验容器可在 arm64 Mac 上稳定启动；有备份时可只读恢复并用 `sqlcmd` 执行 catalog 查询，无备份时给出明确阻塞诊断。
- [ ] 220 个材料文件有可复核 manifest；162 张表和全部 212 个对象源码有分类索引，重复件和计数差异被记录。
- [ ] 旧→新领域、表、字段、状态、编码和权限映射具有版本化文档与机器可读清单。
- [ ] 迁移控制模型具备前向迁移、实体/服务边界、幂等批次、错误重试、校验和回滚点。
- [ ] 至少完成组织/员工 T0 dry-run：来源读取、脱敏数据质量报告、映射预演、数量/关联校验；无真实备份时用结构化合成 fixture 验证完整管线。
- [ ] 历史工资、考勤、社保的迁移策略明确区分“原样历史快照”“新系统计算输入”“新规则计算结果”，禁止混算。
- [ ] 环境和迁移脚本有单元/契约/PostgreSQL 集成测试，相关 lint/typecheck/build 通过。
- [ ] 不修改生产数据、不提交秘密、不破坏其他任务 WIP；所有临时数据库和容器可确定性清理。

## Out of Scope for T0

- 直接切换生产 HR、正式工资计算、银行代发、税务或社保申报。
- 在没有源备份/只读连接时声称完成真实历史数据迁移。
- 复刻 Delphi/ASP.NET 客户端、FastReport 或旧系统程序单元权限模型。
- 在 T0 一次性完成合同、考勤、社保、培训、招聘和工资全部新业务页面。
