# Codex Review 4785450293 防回归复盘

## 1. 根因分类

- 主要根因：测试覆盖缺口。已有验证覆盖了主流程，但没有形成“来源实时性、重试顺序、跨模块兼容、时间边界、计量换算”的完整逆向场景矩阵。
- 次要根因：同一业务规则分散在多个模块。表计启停和倍率、共享占用与历史商业租约、实名登记快照与 Party 当前状态分别存在多个读取入口。
- 过程根因：大型 PR 在每轮修复后继续产生新的可审查表面，逐条修补没有自动保证同类入口全部同步。

## 2. 本轮暴露的失败模式

1. 表计计划只检查启用标记，遗漏业务状态；出账按原始读数差计费，遗漏倍率。
2. 退房交割先校验余额再识别已完成记录，导致成功后的重试可能失败。
3. 入住交割接受了只属于退房的金额字段，形成无对应财务动作的历史数据。
4. 入住核验信任订单住客快照，未重新检查 Party 当前实名状态。
5. 民宿可售只读取共享占用，遗漏仍然有效的历史商业租约。
6. 服务 SQL 让 PostgreSQL 会话时区隐式决定日期与时间戳的比较边界。
7. 日期范围函数截断原始字符串，使带非法后缀的值被当作合法日期。

## 4. 后续提交前检查法

每条业务规则提交前都回答五个问题：

1. 当前事实来自哪里，是否误用了历史快照？
2. 成功后的同请求或新幂等键重试会发生什么？
3. 同一规则是否在其他模块还有读取或写入入口？
4. 日期、金额、计量和状态是否依赖隐式转换？
5. 是否至少有一个正常、一个边界、一个反例自动化验证？
