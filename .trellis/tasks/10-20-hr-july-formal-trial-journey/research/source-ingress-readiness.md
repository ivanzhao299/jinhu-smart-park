# Research: July source ingress readiness

- Query: Identify a controlled existing ingress that can use the prepared T4 source in a new owned isolated database to produce a genuine same-database T4 receipt and frozen July sources without SQL-fabricated receipts, backup re-analysis/A-B, or whole-history loading; determine July scoping and post-July repeat-import support.
- Scope: internal
- Date: 2026-10-20

## Findings

### Decision

No inspected current controlled entry point combines the already-prepared T4 items/formulas/payslips with a **93-row/month-scoped T4 load** and a genuine same-database T4 receipt. The exact reusable T4 follow-on writer is a one-time, full-archive append, not a scoped replay tool. Existing reconciliation-source API can then freeze selected book/month sources, but requires an already-succeeded same-database T4 operation/control receipt. Therefore the supported reusable sequence today is: existing controlled T4 full-domain rehearsal/ingress (if its source artifacts and parent constraints can be satisfied in a fresh owned environment) → real T4 receipt/control in that same DB → standard payroll source preview/freeze API for July books 34/35 → standard formal preparation/trial. It avoids re-analysis/A-B only if using the already-prepared, hash-bound T4 bundle accepted by the existing full-domain workflow; that reuse was not exercised here.

### Source interface and controlled rehearsal

- `docs/hr/yuzhou-import-interface.v1.json:1-42` describes offline reusable adapters and `/hr/imports/yuzhou/incremental/{preview,commit,status}`. It explicitly bounds the general incremental package to 2,000 items/8 MiB and its admitted adapters list `attendance_insurance_period_payroll_training_plan_reward_performance` as outside the reusable adapters (`scripts/hr-cutover/build-yuzhou-reusable-incremental-package.mjs:55-66`). This establishes that this **general** interface does not import payroll; it does not establish global absence of T4 payroll ingress.
- `scripts/hr-cutover/prepare-full-domain-rehearsal.mjs:88-123,149-168` is an owned-isolated full-domain rehearsal preparer. It requires source backup, source restore receipt, T4 evidence, extract/database setup and a run-owned private project; it configures T4 extraction from the restored SQL Server source and prepares an owned Postgres target. This is a real controlled pathway candidate when prior parent/core receipt and full rehearsals are available, but it does not accept only the three existing payroll JSONL files as an API-ready scoped bundle.
- Dedicated T4 materials exist: `production-import-t4-followon-binding.mjs:4-6,16-28` fixes six files (`scheme-memberships`, `items`, `formulas`, `tax-rules`, `closes`, `payslips`), 46,092 source rows, 1,078,020 item rows and `mode: full_archive`; it also requires fixed archive and hot-window conservation counts. `production-import-t4-followon-private-stage.mjs:14-30` binds a manifest to source backup, mapping contract, restore receipt, source-business hash, exact file hashes, and full 46,092 rows / years 2010–2026. `production-import-t4-followon-writer.mjs:80-101,112-117` requires a valid parent T0-T3 receipt, all T4 target tables empty on first append, full archive, and exact full counts. `execute-production-t4-followon.mjs:25-60` checks runtime/code, target identity/scope, isolated loopback DB credentials and authorization before execution. It intentionally does not support a July/93-only T4 receipt; adapting counts or bypassing its binding would invalidate its evidence contract.
- Parent `prepare-full-domain-rehearsal` creates configuration for a full isolated T0-T5 rehearsal, but use is contingent on the required source restore receipt, T4 evidence, parent/T0-T3 state, matching hashes and runtime boundary. Research confirms this entry point exists; it does not prove it can be run from the privateRoot preflight alone or that the current prepared T4 bundle satisfies every rehearsal input.

### July-only freeze after T4 receipt

- The proper freeze ingress is the existing authenticated payroll API, not the source importer: `apps/api/src/modules/hr/hr-payroll-history.controller.ts:167-198` exposes GET preview, periods and POST `reconciliation-sources`, guarded by `HR_PAYROLL_RECONCILIATION_REVIEW`, idempotency, body-free audit. `hr-payroll-history.service.ts:581-607,650-676` computes metadata/hash preview and calls `hr_freeze_payroll_reconciliation_source` with explicit batch, book and month.
- SQL contract `database/migrations/000319_hr_payroll_reconciliation_source.sql:76-120,129-159` rechecks T4 succeeded receipt and a same-current-database successful migration control, then selects exactly one specified batch/book/month with mapped employee rows and freezes their full snapshot and item payload. Each selected book/month is one immutable source; limits are up to 5,000 snapshots and 200,000 items (`.trellis/spec/api/backend/hr-payroll-reconciliation-source.md:3-10`; migration schema `:8-25`). It validates exact content hash/count and idempotently reuses the source UUID. Thus **the post-ingress source freeze can scope to July and the two books**. It does not narrow or replace the T4 import.
- The existing 93-row candidate plus root-reported source/code hash matches are metadata that can be reused as candidate lineage, but no same-database T4 receipt or July frozen-source IDs were verified by this research. Do not treat candidate hashes as a receipt.

### Repeated import/incremental continuity

- The general Yuzhou reusable import interface supports repeat submissions for its admitted domains, with unchanged facts not duplicated, modern edits preserved, operation-ID recovery and per-package transactions (`docs/hr/yuzhou-import-interface.v1.json:36-42`). Its current builder expressly lists payroll outside its adapters (`build-yuzhou-reusable-incremental-package.mjs:55-66`).
- Dedicated T4 currently declares `APPEND_UNPUBLISHED_T4_FULL_ARCHIVE_ONCE`, fixed source and count invariants, first-empty-scope writer and unique per-operation receipt/control. It has rollback for that append, not a same-batch later-period payroll delta contract. T4 scope’s source bundle includes through 2026, so archive completeness can include post-July rows once, but there is no evidence here of repeated incremental ingestion of later Yuzhou payroll updates while preserving existing snapshot identities/versions. Therefore the original request’s post-July payroll delta/repeated-import behavior remains a real uncovered capability in the inspected ingress contracts; do not infer global absence beyond these inspected paths.

### Minimal reusable path and exact gap

1. Reuse the verified T4 file hashes and matching prepared artifacts, without re-reading/re-analyzing the backup, **only where** the controlled full-domain rehearsal/T4 stage accepts the same bound manifest and full archive counts.
2. In a newly owned isolated environment, satisfy its actual parent T0-T3/core receipt, target identity, runtime and authorization prerequisites; let the existing T4 writer create its real append and same-database receipt/control. Never issue SQL to manufacture receipt rows.
3. Use normal role payroll reconciliation preview/freeze API for the precise July source batch, book 34 and 35, month, and exact count/hash metadata; then continue the already-researched formal candidate workflow.
4. For later source changes, the remaining ingress gap is a payroll-specific, append/revision-safe delta importer with provenance, deduplication and reconciliation semantics. Existing T4 full-archive-once and general ten-domain reusable adapters do not provide that contract. This follow-on work must retain current source receipts and normal business review; it must not weaken the T4 seal/approval boundary.
