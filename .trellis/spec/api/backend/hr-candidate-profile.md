# Candidate profile continuity

## 1. Scope / Trigger
Formal candidate basic details can be corrected throughout the business lifecycle. Existing stage, conversion, assessment and interview commands keep their own behavior. This modern contract does not establish original GroupWeb parity, import permission, actual HR-role acceptance, or payroll acceptance.

## 2. Signatures
GET `/hr/recruitment/candidates/:id/profile`, GET `:id/profile-history?page&page_size`, GET `:id/profile/requisition-options?keyword&page&page_size`, PUT `:id/profile`. All require `HR_CANDIDATE_READ`; options and PUT additionally require `HR_CANDIDATE_MANAGE`. PUT uses route-local `HrCandidateProfileIdempotencyInterceptor`. It caches only an encrypted receipt identity/version, then reprojects the exact immutable saved history snapshot at replay time after current write/sensitive-presence authorization, scoped existence checks and required read audit. Later global changes do not replace the original receipt. The generic idempotency cache must never receive profile plaintext. Service repeats permission checks before SQL. Provided sensitive fields additionally require `HR_CANDIDATE_SENSITIVE_READ`, including explicit null.

## 3. Contracts
Partial PUT requires `expectedVersion>=1` and trimmed nonblank `changeReason<=1000`. Provided candidateNo/fullName/requisitionId cannot be null; nullable source/date/mobile/email/identityNumber distinguish omission from explicit null. Optional empty text normalizes to null. Dates use strict real-calendar YYYY-MM-DD with year0000 rejected. Select PostgreSQL DATE as text; driver Date fallback uses local calendar getters, never UTC ISO conversion of local midnight. Email canonicalization trims/lowercases; mobile and identity remove whitespace/uppercase, identical to create. Transformed DTO instances may materialize omitted optional own properties with value undefined, so presence checks require an own property and a non-undefined value. Protected omissions preserve ciphertext/mask/fingerprint; explicit null clears all three. Canonical no-op is rejected.

Current and frozen historical snapshots expose business values, names, the actual global version, dates and masks. Current permission determines sensitive availability on every read: authorized readers receive decrypted nullable mobile/email/identityNumber, masked readers omit those keys and never decrypt. No ciphertext, hashes or actor user IDs leave the service. History freezes before/after names/state; unrelated stage/conversion changes may leave global-version gaps between profile-history rows.

Actual `DataSource` transactions lock the scoped nondeleted candidate, compare its global version, update precise fields and version, append complete encrypted before/after history and require body-free audit using that same manager. Reads use repeatable-read transactions and required read audits. A changed target requisition must be same scope, nondeleted and draft/open under a shared lock; unchanged historical binding remains valid. Hired/converted candidates cannot reassign. Options are minimal action-owned paginated context, not a generic directory grant. Migration000359 creates immutable scoped history with exact snapshot keys/candidate/version shape checks and no seed/backfill.

## 4. Validation & Error Matrix
Malformed/extra fields, invalid dates, missing reason/version or canonical no-op ->400. Missing permission ->403 before SQL. Foreign/deleted candidate or unavailable target ->safe404. Stale global version, hired/converted reassignment and named `uq_hr_candidate_no` collision ->safe409. Required read audit failure rejects the read; write audit/history failure rolls back current and history. Database history UPDATE/DELETE fails append-only.

## 5. Good / Base / Bad Cases
Good: masked manager corrects only the name, preserving all encrypted contact representations. Base: unchanged closed/deleted historical requisition remains associated while source is corrected. Bad: submitting mask tokens as contact values, silently nulling omitted fields, independent version zero, copying decrypted contacts into JSON/audit, reassigning a hired candidate or silently rebasing an uncertain retry.

## 7. Wrong vs Correct
Wrong: `dto.mobile ?? null` treats omission as clearing; `beforeJson: decryptedProfile` records private contacts; `expectedVersion=0` ignores stage/conversion versions.
Correct: apply only present validated fields, use canonical fingerprints for same-value detection, keep encrypted complete snapshots in append-only history, audit only versions, and compare against the locked actual `hr_candidate.version`.

## 8. Future conversion to employee profile

Conversion locks the candidate and employee before `transferCandidateProfile` reads scoped source triples and locks the target profile, inside the existing conversion transaction. No historical replay/backfill. With no source private facts it creates no empty profile; with facts it requires HR_EMPLOYEE_PROFILE_MANAGE, while automated internal transfer returns no plaintext and does not add sensitive-detail read privileges. The existing conversion permission remains required. Personal contact fields map only to profile personal_mobile/personal_email, never employee work contact fields. Source ciphertext/mask/fingerprint must all be present, canonical and mutually consistent; email >128 or mobile >32 fails explicitly. Identity type is not inferred.

Existing matching fields are retained, missing fields are filled, and unrelated columns remain unchanged. Different values, incomplete existing identity, any deleted/ambiguous profile or identity uniqueness collision cause409 and roll back the entire employee/checklist/conversion/headcount/stage transaction. Caller employee lock serializes profile creation with ordinary profile maintenance. Changed profile increments its global version once; unchanged target keeps its version. Conversion evidence and required same-manager audit contain only source version, profile ID, before/after versions and written column names. No contacts, fingerprints or ciphertext enter these receipts.

Tests: `hr-candidate-profile-transfer.spec.ts` and guarded `hr-candidate-profile-transfer.pg.spec.ts`; the latter requires HR_CANDIDATE_TRANSFER_PG=1, HR_CANDIDATE_TRANSFER_ISOLATED=yes, loopback15432 and unique isolated full-schema database. Real permissions/UAT and original client parity remain separate.
