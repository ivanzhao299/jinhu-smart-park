# 技术设计

## 问题分层

1. 租户初始化：`TenantsService.create` 决定启用模块并为 `TENANT_ADMIN` 派生权限。
2. 认证上下文：登录及 JWT 校验从数据库重建角色、权限、模块与菜单。
3. Web 落点：`resolvePostLoginPath` 当前先选首个 href，布局随后才校验权限与模块，可能直接进入 403。

## 设计原则

- 后端授权是权威来源；前端过滤只改善导航体验，不代替守卫。
- 模块授权与权限授权取交集，不因管理员身份扩大套餐范围。
- 先用运行态或精确测试确认实际 403 来源，再提交最小修复。
- 登录落点使用与侧边栏一致的 `hasPermission`/`hasModule` 语义，跳过不可访问菜单。
- 当没有可访问菜单时落到不会伪造授权的安全首页；若安全首页本身受限，则显示明确的“尚未配置可访问模块”状态，而不是误导性的权限异常。

## 数据流

`POST /tenants` → 解析套餐/模块 → 创建模块授权 → 派生并绑定角色权限 → 创建首管 → 登录 → `/users/me` → Web 选择首个可访问菜单 → 布局再次防御校验。

## 兼容与风险

- 不改变 JWT 结构和密码存储。
- 不改变 Issue #217 的多租户超级管理员选择逻辑。
- 不修改历史迁移；若仅为创建逻辑和导航缺陷，避免新增迁移。
- 重点防止通过 fallback 页面或 `isSuper` 捷径绕过模块授权。

## 回滚

- Web 路由选择和后端初始化修改保持独立提交面，可分别回滚。
- 新增测试固定当前最小授权语义，回滚时能立即暴露 403 回归。
