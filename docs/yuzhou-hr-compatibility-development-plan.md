# 玉舟 HR 兼容迁移与 Jinhu Smart Park HR 扩展开发任务书

## 1. 目标与依据

本任务以本机玉舟集团版 V10 分析资料为旧系统事实基线，以 Jinhu Smart Park 当前 HR 首版代码为新系统基线。目标是：

1. 保留玉舟已被企业使用的业务语义和历史数据可追溯性；
2. 用 Jinhu 当前 PostgreSQL、API、权限、Workflow Inbox 和响应式 Web 技术栈重构，不复制旧 Delphi/ASP.NET 代码；
3. 完成旧 SQL Server 数据迁移、校验、回滚和并行核对；
4. 增加 HR 管理员、部门负责人、员工自助及后续财务/考勤专员等多用户端，落实 API 级原子权限和数据范围；
5. 把旧系统不安全或不可维护的实现替换为现代实现：明文密码不得迁移为可登录密码、动态工资表改为规范化明细、照片/附件改为文件对象引用。

事实依据：玉舟资料显示 162 张表；源码目录实物为 194 个过程文件、16 个函数文件、2 个触发器文件，旧分析报告中的“169 个存储过程”需在真实数据库恢复后按 catalog 口径核验；员工 2949 人、异动 6887 条、合同 802/357 条、五险一金 35008 条、工资约 4.5 万行、附件 1003 条。Jinhu 集成分支的 HR 基础迁移为 000230～000234，覆盖员工基础、目标/汇报、绩效/360、薪酬工资、审批。

## 2. 兼容原则

- **业务兼容优先，物理结构不兼容照实转换**：保留工号、组织编码、异动单号、合同号、工资账套、状态和历史日期语义；不照搬旧宽表和动态列。
- **历史永不删除**：玉舟 `person` 的在职、退休、离职、内退等统一进入 `hr_employee` 与 `hr_employment_event`；旧表名、旧主键和原始值进入迁移映射表。
- **状态机替代直接改字段**：就职/调动/离职/复职必须形成事件、前后快照、审批和审计；不能只覆盖员工当前部门或岗位。
- **权限原子化**：菜单权限、动作权限、字段权限、数据范围分离；前端隐藏不是授权依据，所有 API 重验 tenant/park/本人/负责人组织树。
- **金额不可变**：工资确认后禁止原地修改，使用更正批次；工资项、公式、税率和核算结果都要版本化。
- **证据分层**：代码、迁移、测试、推送、部署、health/ready、UAT 分开记录，不能用其中一项代替另一项。

## 4. 多端、多用户与原子权限

### 用户端

1. HR 管理端：组织、人员、合同、异动、招聘、培训、绩效、薪酬、工资、考勤/社保运营；
2. 部门负责人端：组织树范围内人员、团队目标、汇报、绩效审核、待办；禁止薪资明细、证件原文和跨组织查询；
3. 员工自助端：本人档案可见字段、目标、汇报、绩效、自评、360 答卷、人事申请、已确认工资条；
4. 专项运营端：后续拆分考勤专员、薪酬专员、社保专员、招聘专员，按模块动作授权；
5. 移动端：员工和负责人优先，支持待办、汇报、审批、打卡/请假、工资条，不在移动端暴露高敏感批量管理。

### 原子权限模型

权限至少拆为：`module/page/action/field/data_scope` 五层。示例动作包括 `employee.read`、`employee.manage`、`employment.transition`、`payroll.calculate`、`payroll.review`、`payroll.confirm`、`payslip.self_read`。数据范围包括本人、直属团队、组织子树、指定单位、全园区。敏感字段（身份证、私人联系方式、银行卡、工资项、证件附件）单独字段权限和审计。

## 5. 分阶段开发路线

### 5.1 数据切片执行顺序（轻量优先）

历史数据导入不以开发难度或旧模块名称排序，而以“先建立可复用关系、先交付高收益轻量事实、最后处理最大且最敏感的工资明细”排序。受控执行契约为 `scripts/hr-cutover/contracts/lightweight-first-slice-order-v1.json`，顺序固定为：

1. `T0`：组织、岗位、员工主数据；
2. `T1`：入转调离等任职异动历史；
3. `T2`：合同及合同变更历史；
4. `T5_NONFILE`：不含照片和附件的员工档案、家庭关系、技能、证照；
5. `T3`：考勤、社保及现代请假/加班申请事实；
6. `T4`：工资历史与双轨核对，必须是最后一个数据写入切片。

`T5_NONFILE` 只使用稳定员工映射，禁止文件证据与自动身份归并；照片和附件为独立 `T5_FILE`，始终 `HOLD` 且不计入该顺序。完整 T0→T5 全域 A/B 契约用于最终整体复核，不改变上述分批落地顺序。任何生产历史导入仍需要一次性明确授权，当前固定为 `HOLD`。

### T0：基线、资料和迁移实验室

- 固化旧资料清单、SQL Server 备份校验、表/字段/字典/存储过程索引；
- 建立只读旧库容器和脱敏副本；
- 建立 `legacy_*` 映射、迁移批次、错误、校验和回滚记录模型；
- 产出旧→新字段映射表、编码映射表、状态映射表和数据质量报告。

### T1：员工与组织兼容闭环

- 扩展现有 `hr_employee`：旧工号、旧状态、扩展字段、家庭、履历、技能、证照、照片/附件；
- 组织编码树、岗位/职务/职称和编制映射；
- 就职、调动、离职、退休、复职单据及编号规则；
- HR/负责人/员工三端列表、详情、字段脱敏和组织树数据范围；
- 迁移 2949 名员工、138 个组织节点、6887 条异动，完成数量/关联/抽样复核。

### T2：合同、提醒、招聘、培训、奖惩

- 合同及续签/变更链，试用期/合同到期/生日/证照提醒；
- 招聘人才库与入职转化；
- 培训课程、计划、记录、费用；
- 奖惩记录及与绩效/工资的受控联动；
- 迁移合同 802/357、人才 117、附件 1003，并完成附件哈希和下载权限验证。

### T3：考勤与五险一金

- 考勤导入批次、班次、日明细、请假、加班、出差、异常处理；
- 月历到日明细兼容视图，保留旧符号语义；
- 社保政策版本、员工参保关系、月度基数与单位/个人/补充金额台账；
- 迁移并核对 35008 条保险记录和历史考勤；
- 先只读对账，再启用新系统计算，禁止未经批准直接替代正式薪资。

截至 2026-08-20，T3 的历史数据库兼容层已完成：两次只读抽取哈希一致；144 个月历转换为 4,383 个真实日期，旧符号原值保留，其中明确的“普通班次/晚上班”通过 `yuzhou-v1` 规则映射，`N/N1/N2` 保持待复核，不猜测出勤含义；12 套政策转换为 144 个纵向政策项；35,008 个员工社保快照中 34,787 个装载为不可变期间及 208,722 个六险种分项，216 个因 T0 员工未映射、5 个因年月缺失进入脱敏隔离。六险种金额逐类精确核对、员工摘要不变、同批次拒绝、精确回滚零残留和第二批次重装均已通过。请假、加班、出差、实际打卡流水仍属于后续业务/API 切片，不能把本次月历模板迁移描述为完整在线考勤。

### T4：工资兼容计算引擎

- 账套、工资项目、公式、条件、税率、计算顺序和关账模型；
- 旧 `salary01..35` 动态列转 `payroll_run/payslip/payslip_item`；
- 公式解析器采用白名单 DSL，记录原公式、解析状态、人工复核结果；
- 双轨计算对账：旧结果、新结果、差异原因和批准记录；
- 银行报盘、申报平台、财务总账仍列为后续集成，不在首轮默认开启。

### T5：历史迁移、并行运行与切换

- 全量迁移演练至少两次，增量窗口和停机切换方案；
- 关键表行数、金额汇总、员工状态、合同有效性、工资抽样和附件可读性校验；
- 旧系统只读封存，保留原始备份、映射、日志和回滚脚本；
- 通过 HR、部门负责人、员工三类 UAT 后再切换。

## 6. 每个切片的完成门槛

必须同时具备：需求与非目标、数据迁移/回滚、API/RBAC/DataScope/字段权限、状态机/幂等/并发/审计、桌面与移动页面、单元/集成/PostgreSQL/浏览器 E2E、lint/typecheck/build/security、迁移对账报告、最新 commit SHA、推送 SHA、部署 SHA、health/ready、三类角色 UAT 和已知限制。

## 7. 当前差距与首个执行任务

Jinhu 当前 HR 首版不是空白，已具备员工基础、目标/汇报、绩效/360、薪酬工资、审批和基础权限。但当前仍缺：

- 玉舟字段与历史编码兼容层；
- 合同、异动单号、招聘、培训、奖惩、考勤、社保完整领域；
- 工资账套/公式/税率迁移和双轨对账；
- 旧附件/照片迁移；
- 迁移批次、映射、错误、校验、回滚模型；
- 针对 HR 三端的完整原子字段权限和生产 UAT。

**首个开发任务：`HR-YZ-T0-MIGRATION-BASELINE`。** 先不修改生产数据，建立旧库只读访问、资料索引、目标映射草案、迁移审计模型和第一版数据质量报告。完成后再进入员工/组织兼容闭环。当前 Jinhu 工作树存在未跟踪的 `.trellis` 和 `docs/agent-memory`，且本地 `main` 与 `origin/main` 分叉 23/31；执行开发前必须先做提交谱系和 WIP 保护，不得 reset、覆盖或强推。

## 8. 已批准的 T0 执行方案（2026-08-19）

本机采用 Colima、Docker Compose、PostgreSQL 16 与 SQL Server 2022 Developer 组成双数据库实验室。Homebrew PostgreSQL 保持 5432；Jinhu 一次性目标库监听 `127.0.0.1:15432`；玉舟源库监听 `127.0.0.1:14333` 并以 `linux/amd64` 通过 Rosetta 运行。详细启动、验证、密钥和清理方法见 `docs/yuzhou-hr-migration-runbook.md`。

旧材料已完成全量只读扫描：共 220 个文件、218 个文本文件，7z 归档通过完整性测试且内含 217 个文件；清单使用相对路径和 SHA-256，不保存绝对路径或业务敏感值。2026-08-20 已接收并隔离恢复 SQL Server `.dbk` 备份，`VERIFYONLY` 通过，恢复库保持只读；catalog 实测为 162 表、169 过程、16 函数、2 触发器。下一步执行完整 catalog 导出、全量抽取和行级对账，不另写不可审计的临时导入脚本。

## 9. 现场运行态基线修正（2026-08-28）

只读现场遍历证明，玉舟遗留能力不能再按“客户端加一个员工自助 Web 壳”建模，而应保持三个独立证据面：

1. Windows 客户端负责传统组织、人事档案、入转调离、合同、工资、培训、奖惩、绩效、保险、考勤、招聘和系统设置；系统管理员页面按用户维护模块树权限，普通用户与系统管理员的可见能力不同。
2. 正在运行的集团 Web 版是独立 Classic ASP 站点，并连接独立企业 HR 数据库。现场数据库有 438 张表和 231 个 L1-L3 模块，其中 12 个一级域、100 个二级节点、119 个三级节点；186 个可导航入口全部能在部署源码中找到对应文件。部署源码共 6304 个文件，其中 4026 个 Classic ASP 页面。
3. 下载备份数据库中的 `sysTab`、`func`、`Web_GetSysTab` 和 `Web_GetUserRight` 是另一套较小 Web 菜单/权限证据，不能与正在运行的集团 Web 版合并计算，也不能据此推断两者功能相同。

集团 Web 版的权限模型已经包含模块级 `browse/query/add/edit/delete/state/print` 七类动作、角色模板、用户直授权和部门/部门范围数据权限。现场角色分配明显偏宽，迁移时只保留业务语义，不复制旧用户的叠加授权结果；新系统继续采用员工本人、负责人组织子树、HR 园区范围和专项运营角色的最小权限模型，并对敏感字段读取单独审计。

231 个集团 Web 模块按一级域分布为：组织 8、招聘 23、员工 22、考勤 29、薪酬福利 22、绩效 20、培训 31、事务 29、数据配置 4、决策 16、系统 9、个人办公 18。事务、数据配置和系统管理中的通用 OA 能力允许映射到 Smart Park 的工作流、平台管理或其他独立模块，但必须保留旧入口到新归属的可追溯映射，不能以“不属于 HR 页面”为由直接遗漏。

### 集团 Web 逐功能实施度门禁

`pnpm hr:migration:group-web:implementation-coverage` 对 231 个 L1-L3 节点逐项评分，禁止把“已有目标归属”直接解释成“功能已经复现”。评分只采用可在当前仓库重复验证的证据：

1. 目标归属与迁移责任明确：20 分；
2. 目标生产路由真实存在：20 分；
3. 存在对应 API 业务流：20 分；
4. 存在对应持久化模型或迁移：20 分；
5. 已完成该旧功能的字段、状态、计算和审批规则等价验证：10 分；
6. 已由对应真实角色完成生产或隔离 UAT：10 分。

只有 100 分才允许标记为 `implemented`；60-90 分为 `partial`；低于 60 分为 `mapped_only`。当前源码证据基线为 231 项全部纳管，179 项部分实现、52 项仅映射、0 项达到逐功能 100 分；其中 12 项已达到 90 分规则与字段等价门槛，平均 68.92 分，员工域平均 85.00 分。决策中心的聚合员工统计、结构与流动查询已有独立页面/API/持久化证据，但仍缺旧规则逐字段等价与真实角色 UAT，因此只计入 partial，不得刷为完整实现。这个结果不是对当前 HR 模块整体可用性的否定，而是把旧系统的每个菜单能力拆开，明确指出尚缺真实角色 UAT。后续每一切片必须提升明确的旧功能 ID，不能只增加页面说明或笼统模块状态。

12 项 90 分功能的技术 UAT 采用 `scripts/hr-cutover/contracts/yuzhou-live-role-uat-task-card-v1.json`。任务卡固定 HR 制单与复核分离、部门负责人、员工本人三种业务角色，逐功能列出正向动作和越权负例，并要求桌面 1440×1000 与精确 390×844 两种视口同时验证。对应的 `scripts/hr-cutover/contracts/yuzhou-live-role-uat-api-matrix-v1.json` 进一步把 46 个正负向检查逐一冻结为角色、HTTP 方法、参数化 HR 路由、期望结果和不可省略的业务/越权断言；矩阵必须与任务卡逐项同序且哈希进入 A/B 证据，不能再用一个笼统的“接口已通”或手工 PASS 替代真实动作链。只有 Rehearsal A/B 在两套独立资源上执行同一任务卡和同一 API 矩阵、绑定完全相同的代码/源快照/映射合同三元组、逐项 API/审计/浏览器/敏感扫描全部通过且 P0/P1 为零，外部证据校验器才会把对应 ID 的 `liveRoleUat` 置为真。默认报告不读取外部证据，仍保持 90 分；传入 A/B 证据和预期三元组时还会要求证据代码 SHA 等于当前检出 SHA。机器技术 UAT、旧源语义复核和守恒结果统一进入 hash-addressed `machine_attestation`；不再等待 HR 人工签署，但生产历史导入在真实证据闭环前仍为 `HOLD`。

首个规则等价切片是旧功能 ID 313“工作日志”。现场源码确认旧字段为日志标题、工作日期、工作内容、问题和建议，并支持本人新增、修改、查询、删除与操作留痕。新系统补充独立的标题与问题建议字段，保留日报/周报/月报、主管审核、退回重提和目标关联等新能力；旧版物理删除被替换为仅草稿或退回稿可撤销的软删除，动作链永久留痕。该功能已由 80 分提升到 90 分，待迁移与真实员工/主管双角色 UAT 后才能标记为 100 分。

第二个规则等价切片是旧功能 ID 34“员工入职”。对集团 Web 的 `employee/register` 页面、校验脚本、审批保存类和只读数据库结构交叉核对后，确认旧流程不是直接新增员工，而是“录用人员转预入职 → 填写入职申请 → 提交审批 → 非申请人审核 → 审批同意后确认入职”的分阶段事务。新系统新增独立入职申请台账，保留申请名称、申请日期、计划入职日、试用月数、数字考勤卡号、候选人来源与备注；员工、候选人、组织和岗位全部按租户/园区外键校验，员工与考勤卡在未取消申请中唯一。确认入职只有在申请已批准且员工仍为待入职状态时才可执行，并在同一数据库事务内更新员工状态、入职日期、试用期截止日、考勤卡号，生成玉舟兼容的 `JZ` 任职事件编号和不可篡改动作链。旧版回收站删除被现代化为可审计取消，申请人不能审批本人申请。该功能在完成迁移门禁和 HR 申请/审核/确认三角色生产 UAT 前仍不标记 100 分，生产历史导入继续 HOLD。

第三个规则等价切片是旧功能 ID 35“员工基本信息”。集团 Web 真实 `basicinfo` 新增、编辑、详情、列表与保存类共同确认了身份人口、教育语言、联系方式、职务资格四组字段。新系统不照搬旧版明文证件存储：证件号采用加密正文、脱敏投影和规范化指纹三件套，并在租户/园区范围内防重；出生日期、民族、籍贯、政治面貌、身高体重、婚姻健康、户籍、学历专业学位、语言能力、毕业学校、职务职级、员工类别、技术职称等字段进入受保护员工档案。普通档案读取只得到脱敏投影，具备敏感档案管理权限的 HR 才能读取和修改完整字段，读取字段组进入独立审计。旧源文件只保存相对路径与内容哈希，仓库不记录旧员工值；生产历史导入继续 HOLD。

第四个规则等价切片是旧功能 ID 36“员工转正”。旧系统实际由转正申请表、多人转正清单、审批结果与流程结束双门槛、最终批量变更组成；新系统据此实现草稿、提交、退回、复提、审批、取消、确认状态机，冻结提交时员工清单，并用制单复核分离、幂等写、行锁和单事务完成批量确认。最终副作用只把仍处于试用期的员工更新为在职、写入转正日期并追加不可变任职事件，不沿用旧系统语义混乱的离职标志字段，也不写工资或绩效事实。旧源仍只记录相对路径、内容哈希和规则摘要，生产历史导入继续 HOLD。

第五个规则等价切片是旧功能 ID 37“员工合同”。集团 Web 的新增、编辑、详情、查询、保存、附件和操作记录页面共同确认合同编号唯一、合同类型、员工、期限、起止/签订/转正/生效日期、岗位、工种、部门快照、试用月数、试用与转正工资、备注和合同附件。新系统补齐这些字段，合同草稿允许受控编辑，生效、取消、续签、变更和终止均追加不可更新、不可删除的动作流水；旧版物理删除被替换为可审计取消。合同工资写入单独要求薪酬管理权限，读取单独要求薪酬读取权限；合同附件使用合同 ID 作为受保护业务引用，并沿用本人、负责人组织子树和 HR 园区范围。旧源码证据仅保存相对路径、哈希和规则摘要；在完成 HR 管理员、部门负责人、员工本人和薪酬专员四角色 UAT 前保持 90 分，生产历史导入继续 HOLD。

第六个规则等价切片是旧功能 ID 39“岗位变更”。本切片明确区分两个旧入口：集团 Web 版负责岗位变更申请、审批结果、流程结束与审批后手工生效；桌面客户端以 `readjust` 台账维护 `DZyyyymmxxxx` 编号及入职、调动、离职、复职等统一人事异动历史。新系统保留两者共同业务语义，但不复制两套数据：岗位变更申请采用草稿、提交、退回、复提、批准、取消、生效状态机，审批人与制单人分离；只有已批准且到达生效日的申请才能在单事务中更新员工部门/岗位并追加同编号任职事件。审批后若员工当前归属已变化则失败关闭，要求退回重取快照；旧工资字段与变更标志不在岗位变更中直接写工资事实，而进入独立薪酬变更兼容切片。部门负责人只可办理其组织树，HR 具有园区范围权限，动作证据只追加。旧源证据仅保留相对路径、哈希、字段和规则摘要，生产历史导入继续 HOLD。

第七个规则等价切片覆盖旧功能 ID 42-47“员工离职”六项三级功能。集团 Web 版的离职申请、面谈、调查、交接、工资结算和关闭档案已分别核对页面源码与只读数据库结构；桌面客户端仍作为离职任职事件的最终台账来源，两端证据不能互相替代。新系统以一张离职申请聚合草稿、提交、退回、批准、取消和生效状态，审批人与制单人分离；批准后必须逐项完成或经授权豁免面谈、调查、工作交接和工资结算，最后关闭人事档案，方可在计划日期到达后原子更新员工状态并写入同编号 `LZyyyymmxxxx` 任职事件。跨月修改自动重编编号，审批后员工归属或状态漂移时失败关闭，所有动作只追加且所有写接口具备幂等语义。旧系统锁定登录账号的做法不与档案关闭耦合，改由独立身份访问控制处理；已生效后的入离职清单继续作为后置运营流程，而不是重复生效。六项功能从 80 分提升至 90 分，尚需 HR、部门负责人、员工本人、面谈、调查、交接、薪酬、档案和生效角色的生产 UAT 才能达到 100 分；历史导入继续 HOLD。

## 10. 双源数据迁移基线（2026-08-28）

客户端恢复库与集团 Web 现场库必须作为两个独立来源进入迁移，不得把集团 Web 当作客户端数据库的一组页面。客户端来源保留传统人事及工资历史，已审计 162 表、2364 字段、212 条数据库规则、46 个帮助主题和 915 条授权记录；集团 Web 来源保留企业人事运营，已审计 438 表、5449 字段、215 个非空表和 320406 行，并在专用 `VIEW DEFINITION` 只读账号下确认 768 个视图、340 个过程、9 个函数和 79 个触发器。438/5449 的旧系统兼容口径包含 SQL Server 2005 标记为 `is_ms_shipped` 的 1 张零行兼容表；排除该表会得到 437/5442，但不能据此误报业务数据减少。两者都必须在目标记录上保留 `source_id`、来源业务键哈希和抽取批次，不允许覆盖为一个不明来源的“玉舟数据”。

集团 Web 员工主档为 548 行，其中按旧删除/离职标志得到的在职候选为 134 行。与客户端员工按工号或证件规范化哈希核对后，19 行已有匹配，115 行只存在于集团 Web；全量 548 行中按工号匹配 313 行、按证件哈希匹配 308 行、两者并集匹配 316 行，仍有 232 行无工号或证件匹配。姓名不参与自动合并。匹配优先级固定为证件规范化哈希、工号、人工复核；冲突进入隔离，不自动创建在线员工、账号、审批、消息、工资或绩效记录。

可执行合同为 `scripts/hr-cutover/contracts/legacy-dual-source-reconciliation-v1.json`，验证入口为 `pnpm test:e2e:yuzhou-legacy-dual-source-reconciliation`。合同固定两套 catalog、集团 Web 逐表 `COUNT_BIG(*)` 精确前缀汇总、关键业务表计数、员工核对方程和不可逆证据哈希；旧 `sys.partitions` 汇总只能作为快速估算，不得作为迁移守恒。任何行数、哈希、身份策略或生产开关漂移均失败关闭。下一阶段先在隔离库生成 115 行脱敏人工核对队列并完成字段级来源优先级，再执行双源 load→verify→rollback→residual=0→reload。生产历史导入继续 `HOLD`，普通部署不得调用历史 loader。
