## Fixture 结果

实际策略：沿用 R3 已预授权的**产品管理 API 例外**，无 SQL fixture 直插。

Park A 主链成功：产品 API 创建 Park B、page/action/Track-B 角色及四个 UAT 用户并建立 A scope 角色关系。Park B 扩展失败两次：

1. 第一次已创建 B scope 角色并授予 `housing:tasks:page`，但 B scope 的 `GET /users` 不返回主园区仍为 A 的 switch 用户；数据库只读佐证确认该用户已有 A/B 两条 enabled `rel_user_park`，说明失败点是列表可见性/主园区投影，不是缺少 accessible park relation。
2. 第二次使用仓库支持的 `ALLOW_PASSWORD_RESET=yes pnpm db:bootstrap:admin` 恢复 A scope 管理员；随后产品 API `PATCH /users/:id` 将 switch 用户主园区设为 B 并保留 A/B access，均为 200。再次执行 B 扩展时，脚本先把恢复后的管理员切到 B，`PATCH /users/:id` 返回 `409 Username already exists`；前一次已切 B 的同名管理员记录与恢复出的 A 记录发生冲突。

两次失败均发生在浏览器业务 Case 前。达到 API fixture 同题两次上限后停止，不做第三次写入尝试。
