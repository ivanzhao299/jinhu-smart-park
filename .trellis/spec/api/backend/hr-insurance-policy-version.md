# Immutable insurance policy definitions

Scope: `hr_insurance_policy_version`, migration 000322 and `/hr/insurance/policy-versions`.

- This is durable policy definition storage, not activation, an insurance period, confirmation, correction or payroll publication. Every response explicitly retains `activated=false`. Versions with overlapping ranges require explicit downstream selection; never pick the latest automatically.
- Require park insurance read and amount read for reads; writes additionally require the independent `hr:insurance_policy:version_create` capability in controller and service. Do not put this capability into existing role templates or automatic module-derived grants. Permission catalog provisioning and intended grants must be reviewed with the operational UI before release.
- Require an explicit code/name, variant 1/2, inclusive start/end months and nonempty business reason. Never infer effective dates or use the current month. Normalize display names and require a Unicode letter.
- Exactly one origin is permitted: six explicit modern factors, or one scoped imported policy/version/variant. Missing/NULL rates reject; explicit NULL fixed amounts remain NULL. Rates use fractional numeric(18,6), signed fixed offsets numeric(18,3); canonicalize with BigInt without guessing bases or floating-point arithmetic.
- Source copying locks the parent FOR UPDATE and factors FOR SHARE. Existing FK child insertion must wait for the parent so new factors cannot enter midway. Store the source parent identity/version/variant and source factor hash; freeze the selected factors in the immutable definition. Reject incomplete source policies rather than interpreting NULL rates as zero.
- Store exact definition JSON with a database-generated SHA256, scoped family version number and creator. Database guards reject malformed factors, mismatched metadata, foreign/stale source parents, UPDATE, DELETE and TRUNCATE. No historical table DML or seed/role grants belong in the migration.
- HTTP writes use the idempotency interceptor; durable retries independently serialize `(tenant,park,requestId)`. Repeating a canonical request by its creator returns the same UUID even after source changes. Another creator or changed request content conflicts. Family locks plus a unique key protect monotonic versions under concurrency.
- Required audit uses the same EntityManager as the insert/replay and must commit atomically. Audit only definition hash, version, replay status and activation boundary; never copy rates, amounts or business reason into the log.
- Policy definition reads retain mandatory sensitive-read audits. Return only intended policy fields; do not expose source row snapshots, source factor IDs, accounts or creator identities.
- PostgreSQL tests use an explicitly isolated loopback database with the complete original migration chain. Cover actual AuditService persistence/failure rollback, canonical request replay/conflict, concurrent versions, source FK insertion phantoms, source scope/version/NULL rejection, immutable lineage and SQL mutation guards. Synthetic tests do not accept real JWT roles, current business policy or a payroll month.
