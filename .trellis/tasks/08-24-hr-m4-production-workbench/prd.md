# HR M4 前端生产化与角色工作台

## Goal

把当前偏建设说明的 HR 页面改造成国内中型企业可每天使用的业务工作台：人力资源部处理组织、员工、流程和薪资；部门负责人处理团队目标、汇报、绩效和审批；员工处理自己的档案、目标、汇报、评价、审批与工资条。

## Confirmed facts

- HR 是金湖 Smart Park 下的一级独立模块，不属于集团战略管理。
- M3 已在生产部署，具备员工/团队/园区范围、敏感字段投影、高敏感读取审计和部门负责人最小授权。
- 现有 `/hr` 首页重复展示能力介绍、建设阶段和路线图，缺少待办、指标、风险和高频入口。
- 多个子页面以新增表单开场，不符合“先看现状、再发起办理”的日常工作顺序。
- 390px 首屏存在固定侧栏先显示后收起的问题，可能遮挡正文并造成横向溢出。
- 本阶段复用现有 API 和权限，不伪造经营数据，不修改生产业务数据。

## Requirements

1. `/hr` 必须是权限感知的业务工作台，不展示研发阶段、交付路线、产品宣传或大段制度说明。
2. 工作台按当前账号已有权限组合呈现 HR 管理者、部门负责人和员工自助所需内容，不通过客户端扩大权限。
3. 首页优先展示可执行信息：员工概览、目标/汇报/绩效/360/审批/工资相关待办与状态、常用入口；无权或无数据时显示准确的空状态。
4. 员工档案页改为目录优先：搜索/筛选、员工列表、选中详情为主；“新增员工”和办理表单由明确按钮打开，不常驻占据首屏。
5. 页面文字只保留标题、字段解释、风险提示、空状态和必要操作说明；普通用户不应看到兼容路线或开发计划。
6. 移动端侧栏默认关闭，只能由用户明确打开；首屏、水合、路由切换时不得遮挡正文或产生横向滚动。
7. 所有新交互继续使用共享设计系统、共享 API、分层 403 和现有原子权限；敏感档案、工资和 360 匿名边界不得倒退。
8. 保留玉舟旧数据已迁移后的现有展示语义和 ID，不在 M4 引入破坏性 schema、迁移或批量数据修正。
9. 桌面端和 390px 页面都必须可完成高频查看与办理，触控目标清晰，移动端不强迫使用桌面表格。
10. 提交、合并、部署前执行本地/远端/生产三端一致和并行提交冲突检查。

## Acceptance Criteria

- [ ] `/hr` 不再出现“规划能力”“交付路线”“基础期/执行期/绩效期/薪酬期”等建设说明。
- [ ] 工作台只请求当前角色获准访问的数据；单个可选数据源 403 不把整个工作台错误地变成空白或跳转。
- [ ] HR 管理账号可看到员工概览及其有权处理的业务队列；部门负责人可看到团队相关入口/待办；普通员工可看到个人入口/待办。
- [ ] 所有指标均由实际 API 响应计算，并能追溯到对应列表；没有权限和数值为零在 UI 上可区分。
- [ ] 员工档案首屏先呈现目录和检索，新增/任职办理/敏感档案在明确操作后展开。
- [ ] DashboardLayout 在 390px 初始渲染、完成水合和路由切换三种状态下，侧栏默认不可见；点击菜单按钮后可见，选择菜单或关闭后隐藏。
- [ ] 390px 下 `document.documentElement.scrollWidth <= clientWidth`，主要按钮最小触控高度达到 44px，记录使用卡片布局。
- [ ] 页面级权限拒绝、数据级 403、加载失败和空数据均有稳定且不泄露信息的可见状态。
- [ ] 现有 HR 权限、投影、审计和旧数据兼容相关自动化测试不回归。
- [ ] Web lint、typecheck、build、HR/布局定向测试、桌面与 390px 浏览器验收全部通过。
- [ ] 发布前远端主线无未整合提交，部署 SHA 与目标提交一致，生产健康检查和受保护账号只读验收通过。

## Out of scope

- 新增 HR 数据库表、修改已执行迁移或重新导入玉舟数据。
- 在 M4 内一次性重写薪资、考勤、社保或绩效后端规则；这些继续由后续独立里程碑承接。
- 用演示数据、硬编码数字或跨权限接口拼出“好看”的首页。

## Open questions

- 无阻断项。用户已明确要求进入完整开发；具体角色展示以仓库现有权限合同为准。
