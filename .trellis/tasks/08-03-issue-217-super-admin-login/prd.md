# 修复 Issue 217 超级管理员多租户登录阻断

## Goal

恢复平台超级管理员的无租户参数密码登录：当同一用户名和密码同时命中一个有效超级管理员账号与多个普通租户账号时，登录必须选择唯一超级管理员身份，而不是报“关联多个租户”。

## Requirements

- 从已合并 PR #218 的最新 `main` 基线实施，不修改原脏工作区。
- 仅凭用户名不能获得超级管理员优先级；必须先通过密码、账号启用状态与有效角色关系校验。
- 唯一有效超级管理员候选可跳过普通账号的跨租户歧义，并继续使用其现有用户记录所承载的 JWT scope。
- 没有超级管理员候选时，普通账号现有的跨租户冲突与同租户多园区选择流程保持不变。
- 多个有效超级管理员候选仍视为数据冲突，不得任意选择。
- 补充认证回归测试和可执行 Trellis 规范，防止以后用用户名特判或在密码校验前提升候选。

## Acceptance Criteria

- [x] 唯一超级管理员与跨租户普通账号使用同一用户名/密码时可以正常登录为超级管理员。
- [x] 普通跨租户账号仍返回冲突，同租户多园区账号仍返回上下文选择。
- [x] 多个超级管理员候选仍返回冲突。
- [x] 相关 API 单测、lint、typecheck、build 与 `git diff --check` 通过。
- [ ] 修复提交推送到独立分支，创建关联 #217 的 PR 并请求 Codex review；不自动合并。

## Out Of Scope

- 不把 `sys_user`、JWT 或审计模型改造成无租户结构；当前平台管理员仍使用其持久化的基准 tenant/park scope。
- 不按固定用户名 `admin` 绕过认证、锁定、停用或角色有效性检查。

## Notes

- 复测证据：issue #217 评论 `issuecomment-5163079848`。
- 根因：`AuthService.login` 在密码匹配和启用过滤后，先按 tenantId 做歧义拒绝，未识别已随候选加载的有效超级管理员角色。
