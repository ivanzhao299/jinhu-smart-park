# Android 原生多门户客户端实施计划

## 团队与周期基线

建议配置：1 名产品/业务负责人、1 名 UI/UX、2 名 Android、1 名后端、1 名测试；预计 10–12 周完成试点上线。若只有 1 名 Android 与兼职后端，预计 16–20 周。

## Work Breakdown And Ownership

| 工作流 | 负责人 | 主要交付 |
|---|---|---|
| 产品与业务 | 产品负责人 + 工程/物业/业主代表 | 流程、字段、原型、验收标准 |
| Android 底座 | Android A | Compose 架构、登录、导航、权限、发布 |
| Android 业务 | Android B | 巡检、工单、业主服务、离线媒体 |
| API 与权限 | 后端 | bootstrap、聚合、候选项、幂等与数据隔离 |
| 视觉与交互 | UI/UX | Design System、可点击原型、可用性测试 |
| QA 与发布 | QA + DevOps | 权限矩阵、真机、弱网、灰度、监控与回滚 |

实施时拆成 6 个可独立验收的 Trellis 子任务：移动共享契约/API、Android 原生底座、员工端巡检工单、业主端服务、离线/媒体/通知、试点发布与退壳。父任务只负责依赖顺序和最终集成门禁。

## 阶段 0：业务定版与原型（第 1–2 周）

1. 明确“业主端”是企业租户/业主联系人服务门户，还是园区资产所有方管理门户。
2. 对员工角色、业主/租户角色、园区范围、模块和动作建立权限矩阵。
3. 以邵明洪的工程巡检为首个标杆流程，完成任务列表、执行、照片、异常、提交的可点击原型。
4. 冻结 MVP 页面清单、字段最小集、UAT 账号与性能指标。

交付：权限矩阵、信息架构、原型、API 差距清单、UAT 用例。

退出门：工程部、物业和业主/租户代表完成原型走查；所有 P0 页面、字段、动作、权限和错误态有明确负责人，不存在“开发时再决定”的关键字段。

## 阶段 1：原生底座（第 2–4 周）

1. 将 Android 工程升级为 Compose 多模块结构，保留现有 package id、签名和升级能力。
2. 实现登录、会话恢复、刷新、退出、多园区切换和统一错误处理。
3. 实现 Design System、导航、门户路由、能力门禁、埋点与崩溃采集接口。
4. 建立 Room、WorkManager、图片压缩上传与离线队列。
5. 后端提供 `mobile/v1/bootstrap` 与能力映射契约。

验收门：可用不同角色登录并进入正确空门户；权限撤回后重新同步且无法越权。

详细顺序：

1. 冻结 Gradle/JDK/SDK、Compose BOM、minSdk/targetSdk 和模块依赖图。
2. 建立 `internal/pilot/production` build type/flavor 与环境注入，禁止把 secrets 写入 APK。
3. 实现 API envelope、错误码、request id、authenticator、token refresh 单飞和 401 退出。
4. 实现 bootstrap、门户选择、园区切换、capability registry 与 403 自动刷新。
5. 实现 Design System、通用列表/卡片/表单/状态页、无障碍和截图测试。
6. 实现加密账户分区、Room schema、WorkManager、上传队列和客户端 mutation id。

## 阶段 2：员工端 MVP（第 4–7 周）

1. 今日任务/待办聚合。
2. 工程与安全巡检：开始、检查项、异常、照片、定位、提交。
3. 工单：查看、接单、到场、处理、完成。
4. 隐患快速上报与消息列表。
5. 离线草稿、失败重试和重复提交保护。

验收门：邵明洪使用真机独立完成一整天巡检；核心流程不打开 WebView。

员工端退出门：至少完成 30 个真实/仿真巡检任务，包含正常、异常、断网、定位拒绝、照片失败、重复点击和权限撤回；业务记录、照片、审计和状态日志均与 Web 管理端一致。

## 阶段 3：业主/租户端 MVP（第 6–9 周）

1. 服务/报修快速创建。
2. 我的请求、状态时间线、补充材料。
3. 完成确认、评价、园区通知。
4. 企业、联系人、项目/楼栋/位置候选项与默认值。

验收门：业主/租户代表完成创建、跟踪和确认闭环，且不能看到内部派单和管理字段。

业主端退出门：至少 20 条试点请求覆盖报修、保洁、安防、通行和咨询；每条都能从业主提交进入员工处理，再回到业主确认，内部处理字段在业主响应中不可见。

## 阶段 4：集成与试点（第 9–11 周）

1. 自动化权限矩阵、API contract、Compose UI、离线同步和升级测试。
2. Android 7–最新主流版本、弱网、拒绝权限、低存储和进程回收真机测试。
3. 先内部测试，再工程部小组，再 10–20 名业主/租户灰度。
4. 监控任务完成率、上传成功率、崩溃/ANR、API 错误和用户反馈。

试点分三批：

1. 内测：开发、测试、产品，共 5–8 台设备，至少 3 个 Android 大版本。
2. 员工试点：邵明洪及工程/物业 5–10 人，连续运行 7 天。
3. 双门户试点：增加 10–20 名业主/租户，连续运行 14 天。

每批只在上一批无 P0 缺陷、指标达标、队列无积压后扩大。P0 缺陷定义为越权/数据泄露、业务重复提交、草稿丢失、核心流程不可完成、升级后无法启动。

## 阶段 5：生产切换（第 11–12 周）

1. 发布 v2 生产 APK，登录后下载页继续提供升级。
2. 远程开关分批开放员工端和业主/租户端。
3. 保留 v1 服务兼容窗口至少两个稳定版本周期。
4. 试点稳定后移除核心流程 WebView 白名单，并安排剩余低频页面迁移。

生产切换清单：冻结版本 → release build/签名/哈希 → 内部安装升级验证 → 10% 白名单 → 50% → 100% → 14 天观察 → 移除核心 WebView。每次扩大前核对 crash-free、ANR、上传率、API 5xx、重复提交和用户工单。

## 验证计划

- Android：Gradle lint、unit test、Compose UI test、instrumented test、release build、APK 签名/版本/哈希校验。
- Shared/API：`pnpm --filter @jinhu/shared build`、`pnpm --filter @jinhu/api build`、`pnpm typecheck`、新增移动 contract 与权限测试。
- 回归：登录、多园区、权限撤回、模块关闭、巡检、工单、文件上传、幂等、离线恢复和应用升级。
- 真机：相机、定位、通知、后台同步、弱网、权限拒绝、Android 返回行为。

## Definition Of Done

- 产品：P0 原型、文案、字段和异常流程已签字。
- 安全：权限矩阵、跨租户/跨园区、字段策略、token/日志/缓存专项通过。
- 质量：自动化测试、真机矩阵、升级测试和 14 天试点指标通过。
- 运维：监控、告警、运行手册、下载入口、版本 manifest、回滚开关和 Docker 清理验证完成。
- 业务：员工与业主/租户两个闭环都能在生产真机完成，核心流程不依赖 WebView。

## Weekly Milestones

- W1：范围、角色、P0 清单冻结。
- W2：原型与 API contract 冻结。
- W3：Compose 底座、登录、网络层可运行。
- W4：双门户、园区/权限、离线队列骨架完成。
- W5：员工今日任务和巡检执行完成。
- W6：工单、隐患、照片/定位完成。
- W7：员工端端到端门禁通过。
- W8：业主创建、列表和时间线完成。
- W9：确认/评价、通知及双端串联完成。
- W10：自动化、真机、弱网和安全测试完成。
- W11：员工试点完成，双门户试点开始。
- W12：指标达标后灰度生产；否则延长试点，不带缺陷强行全量。

## 高风险点与回滚点

- 权限映射漂移：以共享 capability manifest 和服务端测试锁定，不允许客户端角色硬编码。
- API 仍按桌面页面组织：先补移动聚合/候选接口，避免客户端串行请求大量管理 API。
- 图片与离线重复提交：业务幂等键、文件哈希和同步回执三层防重。
- 业主数据泄露：服务端数据范围和字段策略专项测试，客户端隐藏不是安全边界。
- 升级故障：远程关闭新 capability；保留 Web 服务和旧 API 兼容，不通过降 versionCode 回滚。

## 启动实现前的评审门

- 用户确认“业主端”的目标人群。
- 用户确认采用一个 APP 内双门户，而非两个独立 APK。
- 产品原型、权限矩阵、MVP 范围和 UAT 人员已批准。
- 本任务经用户明确批准进入实施后，方可运行 `task.py start` 并修改业务代码。
