# 正式工资核算设计

基线：60acaf9f798daf50a9d00fcd78f27b5ecfc3cad4。单代理、单生产写入者，当前另一个候选的发布监视只负责已合并 PR883。

## 数据与业务延续

正式工资账套、项目和规则使用中性业务身份，导入来源只作为追踪关系。原目录的来源方案、来源 ID 和哈希约束保持；现代新规则不伪造来源 ID。沿用导入数据需要明确身份映射，人工维护优先，增量导入不得覆盖人工更改。

引入正式规则集、草稿与追加版本；已批准版本通过同一有效版本解析器供配置、依赖校验、对账和正式核算使用。旧冻结运行继续读取冻结版本。草稿使用 expectedRevision；审批锁父规则集及候选，确保同一时期唯一有效版本。按现有权限规范区分维护与复核。

## 输入与计算

工资期间绑定规则版本、当期员工范围、封账考勤版本、所需的确认社保版本和项目输入版本。员工范围明确包括月中入离职和补结算，不以当前 active 状态代替当期范围。期间薪酬变化需明确折算规则，不默认最后一条薪酬。

复用 hr-payroll-formula-dsl.ts 的定点十进制解析求值、依赖顺序及资源限制，复用 hr-payroll-insurance-source.ts 的当前确认社保版本锁。正式计算不依赖 legacyBatchId、旧工资快照或旧实发金额。直接输入与计算项目必须明确区分，零是明确输入，缺记录不能默认为零。

项目配置明确收入、扣款、税额、实发及汇总角色；避免 summary 重复累计。个税使用明确已确认输入或业务批准的计税规则，不凭记忆植入税率；仅录入税额不能宣称自动计税完成。

当前正式内核提供明确选择的 `line_items_half_up` 策略：货币项目先舍入到两位，其后引用使用该项目舍入值；信息数量保留四位。收入项目合计必须等于应发，实发必须等于应发减扣款减税额。税额、应发、实发各有且仅有一个明确项目，税额可来自确认直接输入。单位缴费独立记录，不计员工扣款。该策略必须经规则版本明确选定，不自动套用于既有历史公式。内核返回自身及现有DSL引擎版本供冻结证据使用。

交易按统一顺序锁期间/规则、员工薪酬、考勤、社保和项目输入，冻结版本与快照哈希。缺件、重复、版本漂移、未定义汇总或计算失败整批回滚。最终工资条舍入与总额一致，全部员工成功后才标记 calculated。确认批次不覆盖，更正批次保留原批次关联。不得执行支付。

## 页面与权限

准备情况、缺项修正、试算、复核、确认、更正使用同一现代业务页面，字段按角色维护。共享 Design System，桌面与390px均可完成关键操作。来源信息不作为禁止正式操作的理由。

## 兼容与发布

既有确认批次和对账冻结证据保持不变；新迁移 forward-only，实施前核对最大迁移编号和触发器。旧请求无法提供完整输入时返回明确准备要求，不能继续创建虚假完整工资。生产发布检查精确合并和运行版本、健康及 Docker 清理。真实规则、月份和金额对照独立验收，代码检查不替代业务等价证明。

## 本阶段落地约束

000347建立中性规则集和草稿/提交/批准/拒绝版本，来源账套只作可空的一对一追踪关系。父锁保护追加与审核，expectedHeadRevision/expectedVersion保护并发；创建者、最终修改作者及提交者均不得自审。批准月份唯一，按指定月份选择已批准生效版本。解析AST/依赖/版本随定义保存并绑定数据库哈希；提交、复核及有效版本消费者重新校验解释证据。原历史对账尚未迁到该解析器，正式批次与页面也尚未接入，不能将该阶段视为完整交付。
